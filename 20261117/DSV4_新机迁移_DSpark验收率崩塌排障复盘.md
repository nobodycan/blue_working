# DSV4 新机迁移：DSpark 验收率崩塌排障复盘（Wiki）

- **日期**：2026-11-17
- **主机**：新机 178.110.22.2（`linux-178-110-22-2`）← 旧机 178.139.22.3（`dev-server`，参照机）
- **模型**：DeepSeek-V4-Flash-0731-w8a8（w8a8 量化 + DSpark 投机解码，num\_speculative\_tokens=7）
- **栈**：vllm-ascend v0.30.0rc2（editable 安装）/ 910B3 ×8 / CANN 9.2.0
- **结论**：根因 = 新机模型目录 `quant_model_description.json` 缺 `optional.quarot` 引用，DSpark 走错 embedding/lm\_head 加载分支。修复后验收率 0.3% → 87.8%（负载），吞吐定标达标。

***

## 1. 现象与"指纹"

迁移后压测定标吞吐 \~520 tps（旧基线 2843 tps，仅 1/5.5），但**回复内容完全正常**（数数、自我介绍都对）。

关键指纹（来自 APIServer 每 10s 的 `SpecDecoding metrics`）：

| 指标                        | 旧机基线                                     | 新机（崩塌）                     |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Avg Draft acceptance rate | 53\~65%                                  | **0.3%**                   |
| Mean acceptance length    | 4.7\~5.6                                 | **1.02**（等于没投机）            |
| 逐位置接受率                    | 1.00, 1.00, 0.85, 0.84, 0.70, 0.47, 0.39 | **0.02, 0, 0, 0, 0, 0, 0** |

**指纹解读是本次排障的第一个方法论要点**：

- "内容正常 + draft 第一个 token 就全错" → 不是 kernel 数值抖动、不是并发/负载问题，而是 **draft 模型加载/计算语义错配**（draft 和 target 看到的输入分布不一致）；
- 若是性能类问题（driver 慢、调度差），验收率不会精确崩到 0——数值是"对/错"二值的，崩塌是语义问题。

> 排障第一步：先把"症状"分类成【语义错配 / 数值错误 / 性能退化 / 资源不足】四类，再选对应手段。本次是语义错配，所以后面所有"性能向"假设都注定无效。

## 2. 排障方法总览：三层收敛

```
第 1 层：静态比对（找"两机到底哪里不一样"）
  CLI 参数 → 容器 env/mounts → 资产 sha256 → 镜像 digest → 运行时 config → 日志归一化 diff
第 2 层：单变量 A/B（对剩余嫌疑逐个做实验证伪）
  r3 expandable_segments → r4 编译缓存 → r5 融合 pass → r6 换镜像版本
第 3 层：根因命中 + 修复闭环
  补 quarot 引用 → rc2 原版参数重启 → 冒烟验收率 → 负载定标
```

每一层都有产出物落盘（脚本 + .out 文件在 `261117/`），保证结论可复核、可回滚。

## 3. 第 1 层：静态比对手段细节

### 3.1 指令级比对

- 两机 `vllm serve` non-default args 逐字 diff → 一致。
- **注意坑**：旧机"当前运行的引擎"≠"基线引擎"。旧机当前是 v10 实验实例（WITH\_MTP=0、mooncake KV），基线参照只能用历史日志 `/home/l00800586/dsv4_serve.log`。取运行时参照先确认它是不是你要比的那一个。

### 3.2 容器/进程环境取证

- `docker inspect`（Config.Env、Mounts）+ 引擎主进程 `/proc/PID/environ` 三份对比：区分"镜像自带 env / docker -e 注入 / serve 脚本 export"。
- 结论：两机容器结构镜像一致、注入差异仅为各自实验变量（expandable\_segments、RUN\_DIR 等），均非根因。

### 3.3 资产全量比对（本案翻车点，也是命中点）

- 75 个权重分片：大小 + 文件名排序 diff → 一致；
- 非分片文件（config/tokenizer/yaml/optional/quarot.safetensors）：sha256 → 一致；
- **但 `quant_model_description.json` 两机 sha256 不同（`4838a071` vs `a507db39`）——比对输出里已经写着，却被当成"无关紧要的元数据"放过了**。它实际是行为开关：`optional.quarot.rotation_map.global_rotation` 引用决定 DSpark 走哪条 embedding/lm\_head 加载分支。
- **教训（本 wiki 最重要的条目）**：资产比对必须"逐文件 sha256 全量清单 + 差异零容忍"，任何不一致都要解释清楚才能放行，"看起来像元数据"不构成放行理由。json 配置差异比权重差异更危险——权重坏了会报错，json 差异会静默换执行路径。

### 3.4 日志归一化 diff（高效的代码行为比对）

不去读源码，先 diff 两机启动日志的"行为指纹"：

```bash
sed -n 'START,+N p' serve.log | grep -aE 'INFO|WARNING|ERROR' \
  | sed -E 's/^[^ ]+ [0-9:]+,[0-9]+ //; s/pid=[0-9]+/pid=X/g; s/\[rank[0-9]\]/[rankN]/g' \
  | sort -u
```

- 去时间戳/pid/rank/数值后 `sort -u`，两机各得一份"纯行为集合"；
- diff 出的独有行直接指向差异模块（本案曾定位到 config 输出行，后经完整行逐字符比对确认两机一致，排除该假设）。
- **方法论价值**：日志归一化 diff 是"低成本代码行为比对"，比读源码快一个量级；但它只能发现"打印出来的差异"，静默的加载分支切换不打印，最终还是靠 3.3 的文件级比对命中。

## 4. 第 2 层：单变量 A/B 实验

对每个存活假设，固定其余变量只动一个，跑同一冒烟用例（`case_smoke.sh`：temp=0 数数请求，前后取 SpecDecoding metrics）：

| 轮次  | 唯一变量                                 | 结果   | 判定                  |
| --- | ------------------------------------ | ---- | ------------------- |
| r3  | expandable\_segments 关/开             | 0.3% | 排除                  |
| r4  | 清 `/root/.cache/vllm` 编译缓存           | 0.3% | 排除                  |
| r5  | 关 fuse\_norm\_quant/fuse\_act\_quant | 0.3% | 排除                  |
| r6b | 换 v0.30.0 正式版镜像（顺带默认融合关）             | 0.7% | 排除（双镜像同崩 → 软件栈整体洗清） |

**要点**：

- 用例固定（同一 prompt、贪心解码），让验收率成为唯一观测量，排除 workload 噪声；
- r6 是"一箭双雕"：换镜像同时验证了"代码版本"和"融合默认值"两个变量族；
- 每个 A/B 都走完整链（`docker rm -f` → HBM 确认回收 65536 → 重建容器 → 起引擎 → 就绪轮询 → 冒烟 → 读 metrics），保证上一轮残留不污染下一轮。
- **操作坑**：`pkill -9` 杀引擎后 NPU HBM 不回收（8 卡全 62G 占用、进程已空），必须 `docker rm -f` 销毁容器强制 cgroup 清理。换引擎一律走"重建容器"而非"杀进程"。

## 5. 第 3 层：根因命中与修复闭环

### 5.1 命中

静态比对第 2 轮（跨会话协作线索）：两机 `quant_model_description.json` 的 `optional` 字段——

```json
// 旧机（正常）
"optional": { "quarot": { "rotation_map": { "global_rotation": "optional/quarot.safetensors" } } }
// 新机（崩塌）
"optional": {}
```

`optional/quarot.safetensors` 文件本身存在且 sha256 一致——**文件在，引用丢**，加载分支静默切换，无任何告警。

### 5.2 修复 A/B 闭环

1. 备份新机原文件（`quant_model_description.json.bak.261117`，可回滚）；
2. 旧机版复制到新机，sha256 复核一致；
3. **回 rc2 镜像 + 原版 serve 参数**重启（与旧机基线严格同构，排除"修复生效是因为顺带改了别的"）；
4. 冒烟：验收率 0.3% → 31\~36%，逐位置恢复衰减模式；
5. 负载定标：验收率 **87.8%**、Mean acceptance **7.15**（7 draft 近满收）、Tier 1（8192×64）**2820.01 tps vs 旧基线 2842.95（偏差 0.81%）** ✅。

> 注意验收率与 workload 强相关（冒烟 31% vs 压测 87.8% vs 旧机窗口 53\~65%），横向对比必须在同负载特征下取数。

## 6. 复盘要点（按价值排序）

1. **症状分类先行**："内容对 + draft 全错" = 语义错配 → 应该把 90% 注意力放在"draft 看到了什么不同的东西"（加载路径、权重、配置），而不是性能/数值向排查。本案在 driver 差异上浪费了多轮实验。
2. **比对差异零容忍**：sha256 清单里任何不一致都要闭环解释。本案根因在第一轮资产比对时就已在输出中，被"元数据无所谓"的偏见放过。
3. **单变量 A/B + 固定用例**：是排除假设的最快手段，且每次实验做全量记录（假设/变量/结果/判定），防遗忘防串轮。
4. **归一化日志 diff**：低成本行为比对，适合大日志两机对照。
5. **换引擎 = 重建容器**：HBM 不随 pkill 回收，残留显存会造成 OOM 假象。
6. **共享机器协作**：排障期间机器上有他人会话并行（也清过缓存、留过备份）。动共享资源前 `w` 查会话、留 .bak 可回滚、操作日志留痕（AGENTS.md 铁律的价值在共享环境放大）。
7. **参照物要验明正身**：确认"当前运行的实例"就是"基线实例"（本案旧机基线引擎已死，当前是 v10 实验实例，直接拿它当参照会引入第二组差异）。

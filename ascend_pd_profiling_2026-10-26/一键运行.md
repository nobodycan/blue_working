# 一份脚本运行：AISBench + msprof

脚本：[oneclick_aisbench_msprof.py](oneclick_aisbench_msprof.py)。**只需这一个 Python 文件，Linux / Python 3.9+，不新增 pip 依赖**；沿用机器上已有 AISBench、wrapper 和 CANN。单文件中包含远端采集助手，无需再往 P/D 复制第二个脚本。

固定你的普通模式实验：128K 输入、1K 输出，C=1/2/4/8/16，N=4C。默认每档分别做 P 和 D 诊断，共 10 轮；保留原 AISBench API 模板，通过原代理发压，不改模型参数。

## 1. 生成一次配置

在 **已有 AISBench Python 环境的 Linux 客户端** 执行：

```bash
python3 oneclick_aisbench_msprof.py --init profile.json
```

编辑 `profile.json`，至少填下面这些项：

| 项目 | 填什么 |
|---|---|
| `tools_dir` | 你已成功使用的 aisbench_auto_tools_prefix 目录 |
| `dataset_pattern` | 原始 full 数据文件的绝对路径，可用 `{C}`、`{N}`；例如 `/data/bench/full_C{C}_N{N}.jsonl` |
| `targets.P.pid` / `targets.D.pid` | 各自容器中**实际用卡 worker** 的 PID，不能填 API 主进程 |
| 每侧 `metrics_url` | **从客户端能访问**的 P/D `/metrics`，用于等候真实请求到达；不是 proxy 或 KV 端口 |
| 每侧 `container` / `ssh_host` | 按下表选择连接方式 |
| `cache_note` | 如实记录原 P/D cache、prefix 与跨轮准备方式 |

若已有文件名不带 C，只带请求数，也可以写 `/data/bench/GSM8K-in131072-num{N}-实际模型名.jsonl`。脚本不会重新构造或截断数据，实际有效行数必须恰好是 4C。只测试 `--concurrencies 1` 时只需要 C1 的 4 条数据文件。

代理地址、模型名、tokenizer、模板和鉴权继续从原工具的 config.py/default_api.py 获取。脚本为每个 case 复制工具顶层 Python 文件，只追加输出目录与 `default_perf`；它仍会使用原 AISBench 工作环境，**不要同时运行其他 wrapper**。

### P/D 在哪里，连接参数怎么填

| 情况 | `ssh_host` | `container` |
|---|---|---|
| 总控脚本与目标 worker 在同一容器 | 空字符串 | 空字符串 |
| 总控在宿主机，目标在本机 Docker 容器 | 空字符串 | 真实容器名 |
| 另一台机器的 Docker 容器 | 已配好的免交互 SSH 主机/别名 | 远端容器名 |
| 另一台机器的直接进程 | 已配好的免交互 SSH 主机/别名 | 空字符串 |

如果总控本身在容器中且没有 Docker socket，不能仅填另一容器名就控制它；改用能访问宿主机的 SSH 路径，或从有 Docker 权限、同时已有 AISBench 环境的位置运行。

每侧 `python` 与 `msprof` 必须是**目标环境**的可执行文件。Docker exec/SSH 没加载 CANN 环境时，把该侧 `env_script` 填成当前安装实际的 `set_env.sh` 路径；脚本会在目标容器内 source 它，不安装/升级软件。非默认 SSH 端口等设置用你已有的 SSH alias，脚本不交互输入密码。

## 2. 首次只检查

```bash
python3 oneclick_aisbench_msprof.py --config profile.json --concurrencies 1 --check
```

检查不发模型请求，也不开启 profiling。它核对数据条数、msprof 帮助、worker 启动环境、用户身份和动态采集 socket。`msprof --version` 不支持没有关系，脚本不调用它。

**一次性的服务准备仍需你完成：**worker 必须在启动前配置 `PROFILING_MODE=dynamic`；当前服务没有时，按原部署方式安排重启并重新准备 cache。总控脚本不会代替你关闭其他采集会话、删除 socket、提升权限或重启模型。PID 与实际 NPU/rank 的对应关系用已有 worker 日志或 npu-smi 核实。

## 3. 先跑 C=1 的 P/D 两轮

```bash
python3 oneclick_aisbench_msprof.py --config profile.json --concurrencies 1 --execute
```

成功后，跑原五档：

```bash
python3 oneclick_aisbench_msprof.py --config profile.json --execute
```

默认 `--mode diagnostic`：只做诊断，你原先的普通性能报告继续保留。需要额外的每档 OFF 基线加 P/D ON 两轮时：

```bash
python3 oneclick_aisbench_msprof.py --config profile.json --mode both --execute
```

五档共 15 轮，128K 请求可能耗时较长。只采 P 或 D 用 `--roles P` 或 `--roles D`。不加 `--execute/--check` 时只校验本地输入并打印计划，不访问服务。

## 4. 脚本自动完成什么

1. 按 C/N 创建独立 case，保存数据哈希，保留原 API 模板。
2. 可选地调用你的 cache 准备命令，再单独做公共 prefix 预热。
3. 在实际服务容器启动 msprof attach，用伪终端等交互提示。
4. 启动原 AISBench/wrapper 请求，等角色的 running-request gauge 大于 0。
5. 按角色设定的延迟/时长发送 start、stop、quit，并调用 export。
6. 检查原生报表成功数恰好为 N、失败为 0，以及本次 PROF 目录非空。
7. 保存控制日志、AISBench 报告、case.json 和总索引；异常时尝试停止采集，并终止**它自己启动的客户端进程组**，不向模型 worker 发终止信号。

若指标名与当前镜像不同，把 `active_metric` 改成真实的 running-request gauge。P 默认见到活动立即采，D 默认再等 2 秒；`capture_seconds` 默认 5 秒，可按阶段调整。**running>0 不能证明已进入纯 D，也不保证窗口覆盖完整的 128K prefill**，最后要看 timeline。

msprof 的提示符与错误消息随版本不同。如果等待交互提示超时，日志在服务端 case 的 `msprof.log`；配置允许设置该侧 `prompt_regex` 和 `failure_regex`，只按实际文本调整，不能为了忽略采集失败而删除错误检测。脚本的 PTY 自动化尚未在你的 CANN 版本实测。

## 5. Prefix / cache 怎么接入

- 原来没有 prefix 预热：`prefix_dataset` 留空，服务配置不变。
- 原来有公共 prefix：`prefix_dataset` 填保存好的配对 prefix JSONL，预热单独执行、不计入 4C，也不采它的 NPU 窗口；有多个 prefix 时核对其条数和 `prefix_warmup_concurrency`。
- `before_case_argv` 可填你**已有且验证过**的 cache 准备命令，例如 `["bash", "/data/prepare_cache.sh"]`。它从客户端运行，环境中提供 `C/N/ROLE/PHASE/CASE_DIR`，也支持在参数中使用这些 `{占位符}`。配置了 prefix_dataset 时，该 hook 先运行，随后才是 prefix 预热。
- 留空 hook 不代表 cache 自动重置。相同 full 数据重放可能让 suffix 热化；脚本始终将 `cache_equivalence_verified` 留为 false，不自动生成误导性的 OFF/ON 性能提升结论。

## 6. 结果在哪里

客户端结果默认在 `runs/oneclick/时间戳_唯一ID/`，各 case 有 `case.json`、`events.json`、`console.log`、原生 AISBench 输出和复制的工作配置。全部成功后生成 `index.csv`。

大体积 NPU 数据留在对应服务环境的 `output_root/同一RUN_ID/CASE/`，确切位置写入 case.json/index.csv；**不自动通过网络搬运几 GB 的 trace**。`index.csv` 不是延迟/吞吐替代报表；性能数字仍取原生 AISBench，NPU 关键路径用 Insight 看。

结果可能含原工具鉴权配置，输出根目录设为仅当前用户访问，不要将整个 runs 目录公开上传。

脚本不自动判断实际 token 长度、kernel 阶段、纯 D、全部 rank 性能或 prefix 等价性。`CAPTURED_NEEDS_INSIGHT_REVIEW` 表示原生请求计数和原始数据存在性通过检查，仍需核验时间线。遇到 `UNCERTAIN_STOP_CHECK_SERVER` 时，不继续下一档，先确认服务侧采集停止。

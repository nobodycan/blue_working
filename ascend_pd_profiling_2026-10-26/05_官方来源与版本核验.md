# 来源与适用边界：AISBench 原负载 + 服务端 Profiling

核对日期：2026-10-26。用户现场 msprof 未提供版本号、`--version` 不可用，因此没有将某一版 CANN 的全部参数当作现场已验证能力。

## 1. 本版已知的用户工况

AISBench 与 `aisbench_auto_tools_prefix` 已完成一次普通模式评测：ISL=128K、OSL=1K，C=1/2/4/8/16，N=4C。未确认的信息包括 CANN/msprof 版本、prefix/cache、MTP 和卡分配。本包不据此补造跑分或默认稳态。

核实的重要行为：指定现成 dataset 不等于按 data_num 自动裁剪；现成 full 数据与 prefix_test 的预热路径需单独核实；wrapper 会修改本地 AISBench 配置/数据链接。现场分支若不同，保存实际源码哈希，不直接覆盖用户已有可用模板。

不同 CANN 版本对单卡/多 PID 的支持描述不同，所以第一轮采用单个明确的用卡 worker；不能据新文档宣称旧安装一次覆盖所有 rank。没有证据表明 `msprof --version` 是所有版本通用的接口，本包已移除它作为正常能力检测的依赖。

msprof 的 AI 任务采集必须面向实际 NPU 执行进程。将 `--application` 包在 HTTP 客户端 AISBench 外，不等于采到了 P/D worker。旧 `python -m ais_bench --model xxx.om --profiler 1` 文档属于另一类离线推理流程，不能直接套在本次服务化 AISBench/wrapper 上。

## 4. vLLM-Ascend 备选路径的精确版本

- [v0.30.0rc2 服务 profiling 指南](https://github.com/vllm-project/vllm-ascend/blob/v0.30.0rc2/docs/source/developer_guide/performance_and_debug/service_profiling_guide.md)：profiler 配置、P/D 独立控制、解析路径。
- [v0.30.0rc2 TorchNPUProfilerWrapper](https://github.com/vllm-project/vllm-ascend/blob/v0.30.0rc2/vllm_ascend/profiler/torch_npu_profiler.py)：CPU/NPU、Level1、PipeUtilization、TEXT 导出与 daemon 冲突检查。
- [vLLM v0.30.0 ProfilerConfig](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/config/profiler.py)：路径与 stack/memory 配置；字段存在不等于所有 backend 均同样使用。
- [MS Service Profiler](https://github.com/Ascend/msserviceprofiler/blob/master/README.md)：需要服务请求、调度或 KV 关联时进一步使用；不作为本轮必须安装项。

这些接口用于服务端采集，不改变本轮的 AISBench 客户端和数据集。

## 5. 本包自己的实验建议

C=1 和 C=8 的第一轮选择、3–5 秒有效试采、P/D 先分侧后扩 rank，以及 OFF/ON/OFF 的安排，均是基于已有工况的实验设计建议。它们不是硬件性能保证，也不是“最常用工具”的统计排名。

本轮没连接目标机，没有验证实际 msprof attach、NPU 数据、tokenizer、AISBench 报表和采集开销；所有现场结论都必须由实际文件支持。

# 操作手册：沿用 AISBench 普通模式，增加服务端采集

以下操作在 A2 的 Linux 容器/服务器执行。你已有可运行环境，本版不要求重新安装 AISBench、重新生成所有数据或升级推理服务。

## 1. 本轮参数先定死

```bash
export TOOLS=/你已使用的/aisbench_auto_tools_prefix
export GUIDE=/你放置本方案的/ascend_pd_profiling_2026-10-26
export EXP=/data/pd_profile_aisbench/session01
export PD_BASE_URL=http://实际代理IP:1999
export P_BASE_URL=http://实际P服务IP:8100
export D_BASE_URL=http://实际D服务IP:8200
mkdir -p "$EXP/environment" "$EXP/cases"
```

P/D URL 是 API 端口，不是 KV 传输端口。与原已测链路一致，容器内 localhost 不能跨网络空间混用。

原始五档为 C=1/2/4/8/16，N=4/8/16/32/64；ISL=131072，OSL=1024，普通模式。原始 request_rate、模板、retry、prefix/cache 和生成参数继续沿用；下文的 `--request_rate 0`、`--test_type stream` 是上游常见路径，若你的成功命令不同，应保留自己的值并记录，不能静默改动。

## 2. 记录已有工具和采集能力

客户端：

```bash
cd "$TOOLS"
python3 -m pip show ais-bench-benchmark transformers > "$EXP/environment/client_packages.txt"
python3 aisbench_test.py --help > "$EXP/environment/wrapper_help.txt" 2>&1
ais_bench --help > "$EXP/environment/aisbench_help.txt" 2>&1
sha256sum aisbench_test.py config.py default_api.py generate_dataset.py save_file.py \
  > "$EXP/environment/wrapper.sha256"
```

`config.py` 的原始内容可能含鉴权信息，内部保存即可，公开分享前脱敏。不要在同一 AISBench 工作目录并行启动多个 wrapper，它会改写配置并切换数据链接。

P/D 各自容器留档：

```bash
command -v msprof
readlink -f "$(command -v msprof)"
msprof --help > /你本侧结果目录/msprof_help.txt 2>&1
python3 -m pip show vllm vllm-ascend torch torch-npu
npu-smi info
```

你已确认 `msprof --version` 不可用，不再把它作为前置检查。详细版本和 PID 检查见 06。已有 `collect_env.py` 也可以用来记录环境；它会保留命令报错，不因 version 不支持就判断工具不可用。

## 3. 把上一轮数据和配置变成可复现实验

每个 C 准备上一轮已验证的 full 数据文件，实际有效行数必须等于 4C。如果没有保留数据文件，先按原参数重建一次并留档，随后 OFF/ON 都使用固定文件或定义清楚的等价 cache 方案。

以 C=8 为例，修改路径：

```bash
export C=8
export N=$((4*C))
export FULL_DATA=/你上次C8使用的32条完整数据.jsonl
export CASE_DIR="$EXP/cases/C8_OFF_r1"
mkdir "$CASE_DIR"
python3 - "$FULL_DATA" "$N" <<'PY'
import json, sys
from pathlib import Path
p = Path(sys.argv[1])
lines = [x for x in p.read_text(encoding='utf-8').splitlines() if x.strip()]
assert len(lines) == int(sys.argv[2]), (len(lines), sys.argv[2])
for line in lines:
    json.loads(line)
print('JSONL rows:', len(lines))
PY
sha256sum "$FULL_DATA" > "$CASE_DIR/dataset.sha256"
```

这只核对 JSONL 和条数；实际输入输出长度仍看 AISBench 明细与服务端 usage。128K 输入加 1K 输出的上下文要求保持原来已验证配置，不在本轮顺便改 max-model-len。

保存当轮 `config.py`、`default_api.py`、生成的 `temp_api.py` 和 AISBench 原生报告。wrapper 在 config.py 中的 `OUTPUT_DIR` 必须指向当前 case 的目录：

```python
# 只调整既有 config.py 的输出目录这一项，其余沿用你的成功配置。
import os
OUTPUT_DIR = os.path.join(os.environ['CASE_DIR'], 'ais_outputs')
```

若原配置已按 CASE_DIR 生成目录，无需再改。普通模式应使用上次成功的 summarizer（通常为 `default_perf`）；**本轮不设 stable_stage**。不要只 export 一个未被 config.py 读取的变量就认为生效，要核对 wrapper 日志中的真实 ais_bench 命令。

## 4. 有 prefix 预热时先拆开，原来没有就跳过

先记录原服务 P/D 的 prefix cache 开关。`dataset_type normal` 是客户端数据路径，不能据此断言服务缓存关闭。

如果此前采用公共 prefix 预热，按原方案先发 prefix 文件，待它完成，再发 full 数据。预热使用独立 case，不包含在 N=4C 中。以下仅为已经保存了配对 prefix 文件时的常见写法：

```bash
export PREFIX_DATA=/与FULL_DATA配对的公共prefix.jsonl
export CASE_DIR="$EXP/cases/C8_PREWARM_r1"
mkdir "$CASE_DIR"
cd "$TOOLS"
python3 aisbench_test.py \
  --dataset "$PREFIX_DATA" --dataset_type normal \
  --input_len 131072 --output_len 1 --data_num 1 \
  --concurrency 1 --request_rate 0 --test_type stream \
  --repeat 1 \
  2>&1 | tee "$CASE_DIR/console.log"
```

prefix 文件实际条数/长度以文件为准；若原来有多个 prefix，沿用其原预热并发和条数。不要在正式发压期间清 cache，也不要把预热算进 profile 的 P 热点。

**现成 `--dataset FULL_DATA` 不与 `--prefix_test` 机械组合。** 查阅的上游路径在指定现成 dataset 时不会自动给出配对 prefix 文件，`src_file_prefix` 为空；因此使用显式 prewarm 和 main 两次调用。若现场分支修复了该行为，以源码为准。[上游执行路径](https://github.com/rayn-zzz/aisbench_auto_tools_prefix/blob/main/aisbench_test.py)

## 5. OFF：复现原普通模式结果

P/D 无活动 profiler 后，先完成和上一轮一致的 cache/预热准备。示例重放现成数据：

```bash
export CASE_DIR="$EXP/cases/C8_OFF_r1"
cd "$TOOLS"
set -o pipefail
python3 aisbench_test.py \
  --dataset "$FULL_DATA" --dataset_type normal \
  --input_len 131072 --output_len 1024 --data_num "$N" \
  --concurrency "$C" --request_rate 0 --test_type stream \
  --repeat 1 \
  2>&1 | tee "$CASE_DIR/console.log"
```

此处 normal 仅用于重放指定 full 文件，不重生成数据，也不改变服务端 cache。若原成功命令使用 prefix_cache 并需要保存其标签/逻辑，保留原值及相关参数，只确保不混入 prewarm。wrapper 的 `--npu_num` 若原来有，保持实际值；它用于报表归一化，不分配设备。正式报告优先用整套 PD 的总吞吐，单卡归一化单独标注分母。

wrapper 内部也可能使用管道，仅外层 pipefail 不能保证检测所有内层错误。运行结束必须检查原生 AISBench 的 Success/Failed Requests、有效统计样本和实际 token，不以 wrapper 退出码或其 CSV 一行数据认定成功。

```bash
cp temp_api.py "$CASE_DIR/generated_model_config.py"
cp aisbench.log "$CASE_DIR/wrapper.log"
cp default_api.py "$CASE_DIR/default_api_snapshot.py"
```

wrapper 的 CSV 是附加信息。上游解析存在缺失值占位，不以其 99999/9999 等占位数据做性能结论；以原生报告、明细和日志为依据。[结果解析源码](https://github.com/rayn-zzz/aisbench_auto_tools_prefix/blob/main/save_file.py)

## 6. ON：同负载增加服务端采集

先选主路线或备选路线，**一轮只用一种底层采集器**。如果为了采集重启了服务，先重新做该环境下的 OFF，再进入 ON。

### A. 使用 msprof：推荐从现有安装尝试

完整操作见 [06_msprof动态采集操作.md](06_msprof动态采集操作.md)。顺序是：

1. 核对 help、CANN、真实 worker PID 和启动前的动态环境。
2. 在 P 服务容器 attach 一个确定用卡的 P worker，进入交互界面，先不 start。
3. 创建 C1_ON_P_r1 或 C8_ON_P_r1，恢复与 OFF 等价的 cache 状态，通过 **原 AISBench/wrapper 命令**发压。
4. 等看到目标 P 阶段实际开始，在 msprof 交互界面 start，收短窗口后 stop，再 quit。
5. 为 D 新建同工况 case，选择有效 D 生成阶段采集。先分侧便于确认；多侧多 rank 同采须按现场版本和 device 约束安排。
6. 等各采集器明确停止，AISBench 自然结束，保存原生报告与 msprof 目录。

msprof 与 AISBench 没有靠同名参数自动建立窗口关联。记录 wall clock 作为事件索引，再用 trace 元数据/校时/框架事件核对时基；不能凭终端时间字符串精确相减设备 timestamp。

### B. 使用 vLLM 内置 profiler：适合框架关联和 attach 条件不成立时

在 P 原启动命令中加入：

```bash
--profiler-config '{"profiler":"torch","torch_profiler_dir":"/data/pd_profile/torch/session01/P","torch_profiler_with_stack":false,"torch_profiler_with_memory":false}'
```

D 使用独立目录 `/data/pd_profile/torch/session01/D`。启动后按原配置预热；不改变 TP/EP、MTP、runner 或图模式。确认无 msprof 动态采集正在运行。

v0.30.0rc2 wrapper 已使用 CPU/NPU、Level1 和 PipeUtilization，无需虚构 `--profiler-level`。[精确版本源码](https://github.com/vllm-project/vllm-ascend/blob/v0.30.0rc2/vllm_ascend/profiler/torch_npu_profiler.py)

在有 AISBench 流量且处于目标阶段时，控制终端执行：

```bash
python3 "$GUIDE/scripts/profile_window.py" \
  --p-url "$P_BASE_URL" --d-url "$D_BASE_URL" \
  --seconds 5 --out "$EXP/cases/C8_ON_torch_controls" --execute
```

此脚本**只控制 HTTP，不发推理请求，也不控制 msprof**。P/D 用不同物理 device 且无其他采集任务时才同时采；如果只采一侧，可以手动调用该侧 API：

```bash
curl --fail --max-time 300 -X POST "$P_BASE_URL/start_profile"
# AISBench 已在运行；用独立终端观察 5 秒有效工作后再停止。
curl --fail --max-time 300 -X POST "$P_BASE_URL/stop_profile"
```

D 改 D_BASE_URL。业务流量仍发 proxy。HTTP 404 先查 profiler 配置和直连端口；普通 PD proxy 未必转发这些开关。

停止且导出完成后，在同版本 torch_npu/CANN 环境解析：

```bash
python3 "$GUIDE/scripts/analyze_profiles.py" /data/pd_profile/torch/session01/P
python3 "$GUIDE/scripts/analyze_profiles.py" /data/pd_profile/torch/session01/P --execute
```

D 同理。该脚本不适用于纯 msprof 的 PROF_XXX 根目录。

## 7. C=1 与 C=8 分别抓什么

| case | 数据条数 | 采集目标 | 首轮窗口 |
|---|---|---|---|
| C1_ON_P | 4 | 一条请求中有代表性的 128K P 执行 | 先 3–5 秒确认有 kernel，再按阶段调整 |
| C1_ON_D | 4 | 同工况 D 连续生成 | 5 秒左右，不把接收等待自动排除 |
| C8_ON_P | 32 | 多请求 P 处理与供给节奏 | 中段实际有工作时采 |
| C8_ON_D | 32 | D 的计算/通信/等待及 rank 差异 | 中段实际有工作时采 |

这些采集区间未必覆盖完整请求，也未必是严格稳态。记录真实覆盖范围，原生报告依旧按普通模式给整轮统计。

## 8. 是否要增加请求数

只有在实际诊断发现 4C 无法提供目标窗口时，另建 `EXTENDED`：固定输入输出、并发及 cache 条件，单独增大 N，说明目的是延长采样。它可以继续用普通模式，也可以作为新的 stable_stage 研究；二者独立报表。

不能把 EXTENDED 的窗口吞吐、AISBench 普通整轮吞吐、stable_stage 报表吞吐混为一个数字，也不能把窗口所选的并发上限写成 D 实际 batch。

## 9. 结果打包

每个 case 至少保存：普通模式 AISBench 原生报告和明细、wrapper 真实生成配置、数据哈希/条数、cache 准备记录、P/D metrics、worker/rank/device、采集器配置与开关时间、完整原始 PROF 或 ascend_pt、导出结果和截图。

本次不要使用 `summarize_results.py` 汇总 AISBench；它只支持上一版的 vLLM CLI JSON。填 [04_汇报模板.md](04_汇报模板.md)，把 OFF 和 ON 分开。后续如需自动导表，应按你实际 AISBench 输出版本适配。

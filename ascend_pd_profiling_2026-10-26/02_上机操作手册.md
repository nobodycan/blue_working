# 上机操作手册：按这个顺序执行

以下命令是 **NPU 服务器上的 Linux Bash 命令**。本地文件夹传到服务器后执行。已部署的 P/D 服务继续沿用原来的启动脚本，只在诊断副本中增加 profiler 参数；不要用其他模型的启动示例覆盖当前部署。

## 0. 把文件放好，明确终端角色

建议将本文件夹复制到服务器 `/tmp/ascend_pd_profiling_2026-10-26`，或你有空间的持久目录。示例使用 `/data` 保存 trace；自行更换为真实可写且容量充足的位置。

需要 4 类终端：

- P 服务容器：查版本、确认 P 输出路径、启动现有 P 服务。
- D 服务容器：查版本、确认 D 输出路径、启动现有 D 服务。
- 压测终端：能访问 PD 代理，能读取同版本 tokenizer，装有匹配的 vLLM CLI。
- 采集控制终端：能直接访问 P、D 的 HTTP API。可和压测终端同容器，使用不同终端窗口。

同机两个容器里 `127.0.0.1` 可能不是同一个网络空间，先查容器网络/端口映射。1P1D 不能推导卡数，先填写 `configs/environment_template.json`。

## 1. P、D 各保存环境信息

在每个容器里进入本包根目录，分别执行（`--role` 选对应值）：

```bash
python3 scripts/collect_env.py --role P --out runs/env_P \
  --model-dir /你的真实模型目录
```

D 侧改为 `--role D --out runs/env_D`。脚本记录包版本、NPU 信息、CANN 常见版本文件、CLI 帮助、指定模型的小型配置及其 SHA256，不读取完整进程环境、不读取 API key、不扫描大权重。

验收要点：vLLM-Ascend 通常规范化为 `0.30.0rc2`，vLLM 主包版本也要实际记录，不能只看插件名。把镜像 ID、启动命令、可见 device、物理卡分配人工补进环境表。不要为了对齐文档先升级 torch/CANN/vLLM。

两个采集输出目录若最终汇总到同一位置，分别保留 P/D 前缀，避免混淆 rank。

## 2. 配置本次地址和模型名

压测/控制终端执行，**先修改示例值**：

```bash
export PD_BASE_URL=http://127.0.0.1:1999
export P_BASE_URL=http://127.0.0.1:8100
export D_BASE_URL=http://127.0.0.1:8200
export MODEL_DIR=/你的真实模型目录
export SERVED_MODEL=你的API模型别名
export NO_PROXY="${NO_PROXY:-},127.0.0.1,localhost"
export no_proxy="$NO_PROXY"
```

`PD_BASE_URL` 填代理的根地址，不带 `/v1`。P/D 地址填各自 API 端口，不能填 KV 数据端口。跨机时把两侧 IP 加进 `NO_PROXY`。若启用了鉴权，先按你们现有安全配置访问；示例默认可访问的内部服务，不修改鉴权。

```bash
curl --fail --max-time 10 "$P_BASE_URL/v1/models"
curl --fail --max-time 10 "$D_BASE_URL/v1/models"
```

`SERVED_MODEL` 必须与真实 API 模型名匹配。代理未实现 `/v1/models` 并不代表不能转发推理，按其实现判断。先用现有可用客户端确认一条业务请求成功，并检查代理不会把流式输出一次性缓冲到结束。

## 3. 无 profiler：小规模跑通

确认 P/D 没有正在运行的性能采集。先打印命令核对：

```bash
python3 scripts/run_bench.py --base-url "$PD_BASE_URL" \
  --model "$MODEL_DIR" --served-model "$SERVED_MODEL" \
  --concurrency 1 --input-len 1024 --output-len 128 \
  --num-prompts 4 --warmups 2 --purpose smoke --run-id smoke_c1
```

核对后在相同命令末尾加 `--execute` 开始压测。默认仅打印命令。脚本不会启动模型服务，不改部署参数；实际调用官方 `vllm bench serve`，并在运行前检查所需选项是否存在。

默认 tokenizer mode 为 `deepseek_v4`；如果当前部署实际用了其他 mode，显式加 `--tokenizer-mode 实际值`。客户端必须能读取对应 tokenizer，不能用其他模型的 tokenizer 凑长度。

本包使用 `/v1/completions`，以避免 chat template 隐式改变受控输入长度。若你的代理只支持 chat，先补做对应的官方 `openai-chat` 基准适配并统计模板后的 token 数，不能直接把 endpoint 改名就声称输入长度相同。

检查 `runs/smoke_c1/benchmark.log` 与 `result.json`：

- 请求全部成功，没有超时/HTTP 错误或隐式降级。
- 输出实际长度符合期望。`ignore_eos` 仍可能被上下文上限或服务配置约束。
- TTFT/TPOT 有合理的非空值。
- 检查随机数据生成/分词警告；代理没有 `/tokenize` 时，客户端可能跳过服务端长度对齐。精确长度必须进一步以服务端计数/请求记录核对，不能把命令行期望长度当成已验证实际长度。

## 4. 无 profiler：逐档扫并发

先做 1K/128 的 C=1、2、4，确认正常再扩展到 8、16。示例为 C=4，重复编号写进 run-id：

```bash
python3 scripts/run_bench.py --base-url "$PD_BASE_URL" \
  --model "$MODEL_DIR" --served-model "$SERVED_MODEL" \
  --concurrency 4 --input-len 1024 --output-len 128 \
  --num-prompts 100 --warmups 8 --seed 1001 \
  --purpose baseline --run-id base_1k128_c4_r1 --execute
```

每个正式档位重复 3 次（r1/r2/r3），同一次对照保持相同 seed；不同重复可用不同 seed，但 A/B 两组要成对匹配。观察时间/样本不足时增加请求数，不把只做了 4 个请求的 smoke 当正式结果。

`--request-rate inf` 与并发上限控制闭环负载，不等于无限请求数。不要添加 `--profile`；该选项无法保证普通 PD 代理将开关转发到 P/D。

测试时另开终端观察 P/D 日志、HBM、队列、客户端 CPU。可在 P/D 分别运行下面的轻量快照（输出目录需每次换新）：

```bash
python3 scripts/observe.py --role P --base-url "$P_BASE_URL" \
  --seconds 120 --interval 2 --out runs/observe_P_c4
```

D 改 `--role D --base-url "$D_BASE_URL"`。同机每侧运行会重复读取整机 `npu-smi`，自行按卡映射区分；单次 `npu-smi info` 不保证给出所需所有利用率字段，缺失时用平台已有监控。

观察脚本只读 `/metrics` 与 `npu-smi info`。有些代理/部署不暴露 `/metrics`，会记错误供排查，不把缺失指标记成 0。2 秒采样只能看趋势，不代表微秒级 kernel 行为。

## 5. 为诊断给 P、D 增加 profiler 参数

先备份原启动脚本，在计划的诊断运行中增加以下参数。它需要重新启动服务才能生效；**本包不自动重启或停止你的服务**。

P 容器内准备目录：

```bash
mkdir -p /data/pd_profile/session01/P
df -h /data/pd_profile
```

在现有 P 启动命令参数末尾增加（若末尾已有重定向/管道，应加在它们之前，并正确补 `\`）：

```bash
--profiler-config '{"profiler":"torch","torch_profiler_dir":"/data/pd_profile/session01/P","torch_profiler_with_stack":false,"torch_profiler_with_memory":false}'
```

D 同理使用独立路径 `/data/pd_profile/session01/D`。配置中的路径是在 **服务 worker 所在容器内**，不是控制终端的路径。需要持久保存时挂载到宿主机，先查剩余空间。

保留原有 TP/EP、MTP、图模式、量化、cache 和 connector 参数，不添加 `--enforce-eager`，不切 runner。不要在已有 `--profiler-config` 外再重复加第二个，合并原配置即可。

版本说明：v0.30.0rc2 内置 wrapper 使用 CPU+NPU、Level1、PipeUtilization、TEXT 导出。`with_stack=false`、`with_memory=false` 用来控制开销。这里没有虚构一个 `--profiler-level` CLI；若要更改 Level，需要先核查当前版本接口。[精确版本 wrapper](https://github.com/vllm-project/vllm-ascend/blob/v0.30.0rc2/vllm_ascend/profiler/torch_npu_profiler.py)

启动并预热后，检查 `/openapi.json` 是否列出 `/start_profile` 和 `/stop_profile`；有些部署禁用 OpenAPI，只能按日志/实际请求验证。404 先排查 profiler 配置和直连端口，不要反复向代理发送开关。

## 6. 单请求教学采集：先看到完整过程

终端 A 在 P/D 都处于空闲状态时执行（确认 P/D 使用不同物理 device，且无其他采集任务）：

```bash
python3 scripts/profile_window.py --p-url "$P_BASE_URL" --d-url "$D_BASE_URL" \
  --seconds 5 --out runs/capture_c1_short --execute
```

看到 `CAPTURE ACTIVE` 后，立即在终端 B 通过代理运行一条/少量业务请求，或执行：

```bash
python3 scripts/run_bench.py --base-url "$PD_BASE_URL" \
  --model "$MODEL_DIR" --served-model "$SERVED_MODEL" \
  --concurrency 1 --input-len 1024 --output-len 128 \
  --num-prompts 4 --warmups 0 --purpose diagnostic \
  --run-id diag_c1_short --execute
```

这一步受手工切换和客户端分词初始化影响，5 秒可能错过实际推理，只是教学方式。若 trace 无有效工作，不可据此得出“P/D 很空闲”；用下一步稳态方案重采。长输入/慢请求的完整请求不一定被短窗口覆盖，不能假称已经测到整条请求 NPU 耗时。

控制脚本从两侧返回 start 成功后计时；P/D HTTP 调用不是严格同时发生，事件日志保存每侧发起/完成时间供核对。停止导出可能耗时超过窗口；别把 stop 的 HTTP 耗时当模型执行耗时。

脚本会在正常结束和可处理异常时尝试停止已发起采集的侧；网络中断、进程被强杀等不能保证清理。若日志出现失败，**先直接停止对应侧并检查日志后再压测**：

```bash
curl --fail --max-time 300 -X POST "$P_BASE_URL/stop_profile"
curl --fail --max-time 300 -X POST "$D_BASE_URL/stop_profile"
```

若与你自己的采集器共用服务，不要混用控制会话；本脚本不会识别其他人已开启的会话。

## 7. 稳态采集：正式诊断用这个

1. 同配置先不开 profiler 完成预热；确保图编译、模型加载已结束。
2. 终端 B 启动足够长的 `--purpose diagnostic` 压测，例如沿用第 4 步工况，增加请求数以形成平台。
3. 观察 P/D 调度、队列和吞吐进入稳定区间；不要只固定 sleep 若干秒就宣称稳态。
4. 终端 A 运行 `profile_window.py`，先收 3–5 秒。P 的单轮 prefill 较慢时，可扩到 10–20 秒，但应检查输出大小并解释窗口覆盖范围。
5. 等到两侧 stop 成功、数据写出；压测自然结束，单独保存其结果。
6. 校验该窗口 P/D 实际有业务；查看各 rank 文件，不只看目录存在。
7. 另做同工况 profiler OFF 对照。诊断组数字不能填进正式性能表。

如果 C=1 且输出很长，稳定运行中的 P 很可能在等 D，不再做 prefill。要分析 P，必须把窗口对准 P 的实际处理区间，或者在相同工况下延长受控请求序列；不能把抓到 D 的窗口默认当成 P 的有效样本。

分析纯 D 稳态时，选已确认不受 KV 等待/接收影响的 D 区间；仅“从首 token 后开始计时”不足以证明没有传输干扰。完整混合负载诊断则保留传输活动，看它与计算怎样重叠。

## 8. 解析并检查文件

在服务使用的同一套 torch_npu/CANN 容器里执行。先只列出待处理目录：

```bash
python3 scripts/analyze_profiles.py /data/pd_profile/session01/P
```

确认采集已停止、原始数据完整后再实际解析：

```bash
python3 scripts/analyze_profiles.py /data/pd_profile/session01/P --execute
python3 scripts/analyze_profiles.py /data/pd_profile/session01/D --execute
```

脚本对每个具体 `*_ascend_pt` 目录调用官方 `analyse`，不会把含 `*` 的字符串原样传入。已有主要输出的目录默认跳过，避免重复解析；如确实需要重解析，先另存一份原始数据再按 `--help` 使用 `--force`。

不同 CANN/torch_npu 版本输出不同；重点找 `ASCEND_PROFILER_OUTPUT` 下的 trace、kernel/operator 统计、step/communication 数据，或版本对应的 DB。缺少文件先查是否启用对应采集与导出，不要靠空文件凑齐。

## 9. 在 MindStudio Insight 看结果

先把一个代表性 rank 的完整 `*_ascend_pt` 目录取回本地，或用服务器可用的 Insight。保留目录结构和元信息。支持的导入格式及 GUI 操作以安装版本为准。

导入 trace 或目录 → 选一个确定有推理的时间窗 → 看 NPU compute、通信、CPU → 观察空白 → 查看其他 rank → 对照 P/D 和压测事件。具体讲解见 03。

不要把 P 和 D 的 trace 随便平移后宣称同一时间。跨机需 NTP/PTP/chrony 与采集时钟的映射；同机也要核查工具导出时间基准、容器与 rank 标识。

## 10. 汇总正式结果

```bash
python3 scripts/summarize_results.py runs --out reports/benchmark_summary.csv
```

脚本只汇总 `purpose=baseline` 且完整退出的 `result.json`，不混入 smoke/diagnostic。失败数非零仍会写入并标为 `REVIEW`；不完整结果会报错，不能静默当作正常成绩。

汇总后检查实际总 token、各轮请求数、失败数、单位和原始日志。若工具版本缺少某项，保持空白；不要填 0。然后填写 04，保存关键截图和 trace 路径。

## 11. 第二阶段：需要服务链路时

P/D 的 NPU trace 已经能看见空白，但无法解释请求在哪个服务阶段等待时，再使用当前版本支持的 MS Service Profiler。先阅读 05 的版本化指南，保留原有依赖，使用独立实验会话。

大致流程是：给每侧设置独立 `SERVICE_PROF_CONFIG_PATH` / 输出路径 → 按匹配配置启动服务 → 动态切换 enable → 运行同一业务负载 → 关闭采集 → `msserviceprofiler parse --input-path ... --output-path ...`。

解析产生的请求/batch/KV 事件用于对齐框架行为。它不是与本包 3–5 秒 NPU 窗口等同的采集模式；官方服务分析对时长有不同建议，按对应版本设定。不要同时打开多个基于同一底层采集能力的工具。

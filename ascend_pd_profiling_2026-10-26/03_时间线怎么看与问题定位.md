# 时间线怎么看：先找关键路径，再看算子排名

## 1. 打开前先做 5 个核对

1. 这是 P 还是 D？哪个物理节点、哪张卡、哪个 rank？
2. 此工况的输入、输出、并发、MTP、图模式是什么？
3. profiler 采集窗口里确实有模型推理吗？是否只抓到了 idle、分词或初始化？
4. 这份 trace 与哪个诊断 run-id 对应？采集时 profiler OFF 的基线是哪一轮？
5. 文件解析有没有报错？一个 rank 有数据不表示所有 rank 都成功。

MindStudio Insight 的导入格式和视图会随版本变化，优先保留完整原始目录。可以先导入一个代表性 rank，再逐步看其他 rank。[Insight 官方说明](https://www.hiascend.com/document/detail/zh/mindstudio/81RC1/GUI_baseddevelopmenttool/msascendinsightug/Insight_userguide_0002.html)；[目录格式说明](https://github.com/Ascend/msinsight/blob/master/docs/zh/support/faq.md)

## 2. 看图的顺序

先从整个窗口找稳定区间，放大到一个实际模型执行区间，再观察每条 stream。不要一上来就在长表里搜索某个听过的算子名。

| 观察对象 | 先看什么 | 还需要什么证据 |
|---|---|---|
| CPU / host | 下发是否连续，是否出现长同步或调度空白 | 框架事件和 CPU 监控 |
| NPU compute | 哪些 kernel 在执行，持续多久，是否被空白隔开 | kernel 明细、对应算子/形状 |
| 通信 | 与计算重叠多少，是否在关键路径上阻塞 | HCCL/传输事件、相关 rank |
| rank 之间 | 是否某个 rank 持续最晚完成 | 多次同工况 trace，而非单个偶发尖峰 |
| P 和 D | D 等待时 P 在算、在搬、还是已经空闲 | 同一请求/批次标识与可对齐时间 |

PD 的 KV 传输未必都显示为一条明确的 HCCL kernel。Mooncake/connector 可能使用不同搬运与通信路径；**HCCL 总时长不等于 PD 传输总时长**。缺少对应事件时，用 connector 日志、MS Service Profiler 或适配打点补证据，不能给空白随意贴标签。

## 3. CSV 和 DB 哪个先看

| 数据 | 用法 |
|---|---|
| `trace_view.json` / 对应 DB 时间线 | 确认顺序、重叠、空白和关键路径 |
| `kernel_details.csv` | 找单个底层 kernel 的起止、时长和类型 |
| `operator_details.csv` | 在当前版本支持范围内关联框架算子与设备执行 |
| `op_statistic.csv` | 按类型/次数/总时长筛选候选热点 |
| `step_trace_time.csv` | 当前导出确实有有效 step 标记时看迭代分布 |
| communication 数据 | 支持的通信拆解与 rank 分布；不能自动覆盖全部 PD KV 路径 |

文件不保证全部出现；字段、单位和采集级别以你的版本为准。前 4 类文件可用于“找候选”，**真正的端到端影响要回到时间线和对照压测确认**。

## 4. 四个有用的计算

### 4.1 单类 kernel 累计耗时占比

`某类 kernel 时长之和 / 选定集合内所有 kernel 时长之和`。

这回答“被统计的 kernel 工作量主要落在哪类”，不是“请求总延迟中这类占几成”。分母必须明确是某卡、某 rank、某窗口、哪些事件。不同 stream 并发导致时长和大于墙钟时间，不能当作错误强制压回 100%。CPU 算子、NPU kernel 和父子 range 不能混着累计，避免重复计数。

### 4.2 设备活动区间覆盖率

`窗口内设备任务执行区间的并集长度 / 窗口墙钟长度`。

先按 device 筛选、裁剪到窗口、合并重叠区间，再计算。它是“被 trace 覆盖到的活动比例”，**不是实际 FLOPS 利用率，也不等于 npu-smi 的某个利用率字段**。缺失事件、过滤类型和流都会改变结果。

### 4.3 暴露在关键路径上的通信

总通信时长不能直接当延迟损失。先确认哪些通信与计算重叠，哪些等待阻止下一步启动；用依赖和同批次时间线判断。统计时保留“通信总时长”“未被计算覆盖的通信区间”“有证据的关键路径等待”三个不同概念。

### 4.4 改动前后的提升

- 吞吐提升：`(新吞吐 / 原吞吐 − 1) × 100%`。
- 延迟降低：`(原延迟 − 新延迟) / 原延迟 × 100%`。

例如原来 100、新来 120，吞吐提升 20%；这是算式示例，不是本机跑分。使用重复实验的结果与波动范围，且配置、负载、统计窗口保持一致。

## 5. 如何解释常见现象

以下都是诊断假设，不能仅凭左列下结论。

| 现象 | 候选原因 | 下一步验证 |
|---|---|---|
| TTFT 随并发迅速变大，P 排队增长 | P 容量或调度压力 | P 队列/处理区间、关键 kernel、输入长度对照 |
| P 已完成，D 首次执行仍明显等待 | KV 传输、D 排队或握手 | 传输起止/完成标识、D 调度和请求关联 |
| TPOT 明显升高，D 执行很密集 | D 计算/访存/通信压力 | 变更实际 D batch 后的 kernel 和延迟曲线 |
| NPU 经常空白，客户端并发不低 | 等 P/KV、CPU 调度、请求不足或 I/O | CPU、队列、传输、客户端供给同时核查 |
| 吞吐不再提高，但延迟持续增加 | 接近饱和或排队 | 同工况重复、请求队列、成功率和 SLO |
| 部分 rank 明显晚，其他 rank 等待 | 专家负载、通信或硬件/绑定差异 | 专家分布、rank 通信、NUMA/网络和热状态 |
| 开 profiler 后延迟明显变差 | 采集/导出开销，或日志/磁盘竞争 | 相同配置 OFF/ON 比较；缩短窗口，确认无叠加采集 |
| 高并发 TTFT/ITL 尖峰，NPU 无对应停顿 | 客户端 CPU、网络、代理缓冲 | 压测端资源、独立客户端/链路对照 |
| W8A8 并没有期望中的倍数加速 | 非量化算子、量化转换、低效形状、通信占比 | 实际 kernel、量化覆盖和非矩阵部分，而非只看权重名字 |

## 6. DeepSeek / W8A8 / MTP 要额外注意

DeepSeek 的 MoE 路由会影响专家负载；真实文本和随机 token 的表现可能不同。不要只用总参数量估算每 token 运算量。

W8A8 描述部分权重/激活的量化，不保证全模型、所有算子、KV cache 和通信全部按 INT8 运行。应检查量化配置、实际 kernel 和执行形状。量化常伴随 scale/转换、融合或特殊 kernel，不能根据名称把所有非 MatMul 都归类为“无用开销”。

开启 MTP 时，同时报告开关、草稿 token 数、接受情况和实际输出计数。模型 forward 步数、NPU graph replay 次数、流式事件数均不能直接当输出 token 数。

图执行可能让框架调用栈的细粒度关联变少，但不能为了好看直接禁用图后拿该结果代表当前部署。确实需要 eager 诊断时，另做可比基线并标明模式。

## 7. 导师若问“算力利用率 / MFU 怎么算”

先问清楚他指的是 kernel 时间、设备活动、PipeUtilization，还是有效 FLOPS 对理论峰值的比例。它们是不同指标。

v0.30.0rc2 内置采集启用的 PipeUtilization 是硬件执行管线相关指标，不能直接当作模型级 MFU。若算 MFU，需要可信的实际运算量模型、有效运行窗口和硬件在对应精度下的峰值；MoE、稀疏结构、W8A8、attention 与 MTP 都影响分子分母。**不要把 `2 × 总参数量 × token/s / NPU峰值` 不加验证地用于此部署。** 首轮先报告可直接测到的时长、吞吐和管线指标。

## 8. 保存一张截图时附带什么

至少写清：run-id、P/D、node/card/rank、窗口起止、输入/输出、并发、是否稳态、profiler 设置、MTP/图模式，以及截图支持的那一个结论。把源 trace 和原始结果路径同时写入报告，这样截图才可复查。

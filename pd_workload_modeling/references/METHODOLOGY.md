# 昇腾 A2 / aisbench：实测校准的负载建模与优化方法论

## 0. 分析范围与最终目标

计划条件：输入 512；输出 512/1024/2048/4096/8192/16384/32768/65536；并发 1/4/8/16/32；mixed 一机、disagg 两机。共 80 个条件，不含重复运行。

目标不是“证明既定结论”，而是建立可复核的证据链：

```text
真实负载与计时边界
→ 运行级指标与质量审计
→ 可观测的性能响应面
→ 经留出验证的简化模型
→ 服务端观测支持的瓶颈解释
→ 单变量优化
→ 独立复测与回归检查
```

本协议给的是方法，不包含真实结果。行业来源、适用边界与本地方法的区别见 SOURCES.md。

### 三层模型，不可混为一谈

| 层次 | 输入 | 输出 | 证据上限 |
|---|---|---|---|
| M0 经验响应面 | aisbench 同口径独立运行 | 给定部署/C/L 的延迟、吞吐、差值 | 已测范围内的部署表现 |
| M1 半解析模型 | M0 + 实际长度 + 明确负载方式 | 固定项、上下文相关项、有限额外项的候选解释 | 与某种形态一致；参数不自动代表硬件因果 |
| M2 校准结构模型/模拟器 | 算子微基准、调度事件、通信与缓存观测 | 步耗时、资源下界、调度与配置反事实 | 只有经过独立实测校准和验证才可用于预测 |

先完成 M0。只有 80 个汇总均值时，不要假装已有 M2，不训练黑盒大模型取代证据。

## 步骤 0：冻结目标、估计对象与权限

### 具体操作

1. 创建 PLAN.md，填实际服务器栈、模型版本、aisbench 版本和原始路径；未知填 unknown。
2. 主比较限定为“一机 mixed 部署 vs 两机 disagg 部署”。机器数不等，不是等资源架构因果实验。
3. 确定主指标：优先保留并核实本版 aisbench 的每请求响应事件 TPOT，再对独立运行平均；有可靠内容 token 边界时另报规范首末内容 token TPOT。两者独立命名、独立建模，不强迫缺少内容边界的数据进入规范口径。
4. 决定优化目标的优先级：例如先成功率和正确性，再 TTFT/TPOT SLO，再 goodput/成本。SLO 未给出时只提供 Pareto 选择，不宣称唯一最优。
5. 写出：接近容差、长输出范围、平台容差、预测误差容差、重复单位、最大补测预算。看过结果后确定的标准必须标记探索性。
6. 明确权限：本轮默认只读历史数据、生成本地分析；启动压测、采 profiler、改服务参数、量化、重启和上传内部记录均需单独授权。

### 产物与门禁

产物：PLAN.md、STATE.md、permissions.md。

无数据路径时先交付计划；不要搜索磁盘。无 SLO 不阻塞描述分析，但阻塞“满足业务最优”的结论。

## 步骤 1：锁定 aisbench 实现及负载语义

### 1.1 版本锁定

在独立代码目录执行只读版本查询，保存输出；命令失败就保留失败信息，不编造版本：

```text
python -I -m pip show ais_bench_benchmark
python -I -m pip show ais_bench
python -I -m pip show aisbench
python -I -m pip show vllm-ascend vllm torch-npu
```

上面是候选包名查询，不要求它们同时存在。结合原始启动命令、容器标签、安装路径、Git commit 和保存的配置判定真实实现。MindIE 不应被强行识别成 vLLM。

从已安装程序的 --help 和同版本源码确认实际 CLI；不要把网上最新版参数直接拼进历史运行命令。

### 1.2 建立两个语义表

A. 压测语义表：

```text
设定 concurrency、请求总数、是否补请求、请求到达分布
request_rate/ramp/持续时间/预热/冷却
流式/非流式、输入来源、目标输出、EOS/超时
客户端连接池/并发限制/排队起点、失败重试
```

B. 时间语义表：

```text
计划到达时间、实际发出时间、服务端到达时间
首个流式事件、首个内容 token、最后内容 token、HTTP 结束
每个字段的时钟域、单位、是否存在、来源路径
```

### 1.3 必须分清

- concurrency 不等于请求总数，也不等于实际 decode batch。
- 流式 chunk 不一定等于一个真实 token；若一个 chunk 包含多 token，不能伪造等间隔 token 时间戳。
- closed-loop 不是固定到达率：输出变长会降低补入请求频率。
- open-loop 若被客户端并发上限阻塞，实际到达率可能远低于目标到达率。
- 没有服务端时间戳，不能把 TTFT 全部称为 prefill 时间；它可能含排队、网络、调度和 PD 交接。
- 无请求真实到达时刻时，不能排除负载发生器隐藏的等待；客户端已发送后的延迟可能低估计划到达后的延迟。

### 门禁

产物：stack_manifest.json、workload_semantics.md、metric_dictionary.md。

时间单位/起终点不明的指标只作为未核实原值，不进入规范模型。缺少服务端事件只限制机制解释，不阻塞 M0。

## 步骤 2：盘点、标准化与质量检查

### 2.1 文件处理顺序

1. 只扫描用户提供的原始路径。
2. 选 mixed/disagg × 短/长输出及高并发样例，读取结构，不把巨型记录全部送入模型。
3. 明确一个文件对应一个还是多个 run；区分 summary、detail、原始流和日志。
4. 编写 field_mapping.md：真实字段路径、单位、含义证据、转换、缺失处理。
5. 以 (run_id, request_attempt_id) 去重；重试是新尝试，不能与第一次失败覆盖合并。
6. 保存 request-level、run-level 两层表；有事件再保存 token/chunk/server-event 层，不能伪造缺失层。
7. 每次运行关联模型、精度、TP/PP/DP/EP、P/D 资源、调度、KV 配置、预热、时间段。

### 2.2 规范指标

只有同一请求起点和真实内容 token 边界已核实时：

```text
N_i = actual_output_tokens_i - 1
D_i = last_content_token_time_i - first_content_token_time_i
canonical_TPOT_i = D_i / N_i
```

L<2 时 TPOT 未定义，不填 0。若只有 E2E 和 TTFT，先验证 E2E 是否止于末 token；HTTP 结束后的尾部处理不应悄悄计入规范 D。

原始 aisbench TPOT/TBT/ITL 指标使用其版本定义，分别保留，不强迫其与规范量相等。相同名称跨工具也可能不同。标准 aisbench 响应事件 TPOT 可以作为 M0 的合法结果变量，并用于 M1 候选形态诊断；但响应事件包含角色/usage/网络/交接尾部时，逆长度系数可能混有这些边界开销，不能命名为纯 prefill 或纯算子时间。附带脚本通过 --metric-semantics 强制区分两类口径。

运行内同时保留：

```text
请求均值 = mean(D_i / N_i)
token 加权 = sum(D_i) / sum(N_i)
```

先请求到 run，再对独立 run 等权平均。若另外计算请求池化指标，独立命名。

### 2.3 逐项检查

- 80 格覆盖与独立重复数；同一 run 的多个导出不算重复。
- 每格实际输入、输出的 min/median/max、完整目标长度比例。
- 成功、错误、超时、取消、未完成、重试、预热数量。
- 计时单位、时钟域、负时长、NaN/Inf、重复 ID。
- 首末 chunk 是否为空事件；token 计数是否来自最终 usage 或本地 tokenizer。
- 长输出是否提前 EOS、上下文超限、超时截断；65536 输出还需容纳输入和特殊 token。
- 缓存命中、prefix 复用、背景负载、运行顺序是否不平衡。
- summary 与 detail 的口径差异，不能通过篡改数据强行对齐。

失败样本保留并披露，主延迟结果明确“成功请求条件下”。不根据是否符合推论删除异常。

### 门禁

产物：coverage.csv、field_mapping.md、quality_report.md、标准化表。

已发现质量问题逐项标记其影响；未知不能填成 0。有明确失败/不完整运行时不能悄悄消失。

## 步骤 3：建立“负载画像”，不是只有 C 和 L 两个标签

### 必须生成的画像

每个 run 记录：

```text
任务：输入/实际输出/总请求数/输出分布/流式方式
到达：burst/closed_loop/open_loop/unknown、实际发送间隔
在途：客户端已发送未结束请求数的时间序列（有时间戳才重建）
服务：实际活跃 decode batch、prefill 到达/执行事件（有服务端证据才填）
资源：每阶段/每rank NPU数、模型与KV占用、通信拓扑
测量：完整请求群组或稳态事件窗口，不允许混用
```

burst 只发一批时特别检查：prefill 是否全部在首 token 前结束；如果是，不能用这部分 prefill 直接解释首 token 后 TPOT。

closed-loop 特别检查：更长输出是否减少补请求频率、改变 prefill/decode 比例；这与“同一固定扰动被摊薄”是不同机制。

open-loop 特别检查：目标到达率、实际发送率、服务端接收率、完成率和队列是否稳定；存在持续积压时不使用稳态队列结论。

### 测量窗口

主分析优先完整请求群组：从指定群组首个实际发送到最后一个结束，等待该群组收尾；失败状态照实记录。

稳态事件窗口可以另报吞吐/利用率，但不要把仅窗口内 token 的时长除以整请求输出数。记录跨窗口请求如何计入分子和分母。

### 门禁

产物：workload_signatures.csv、measurement_window.md。

无法获取实际 batch 时只建立“设定并发 C 的系统响应”，不能叫 batch-kernel 模型。

## 步骤 4：先画运行状态地图，后谈优化

每个输出长度分别看 C 扫描；每个 C 分别看输出长度扫描。先分 analysis_group，禁止跨配置拼线。

主表至少包含：

```text
mode/C/L/重复数/成功率/实际长度
TTFT、规范 TPOT、E2E、请求TPOT P95（如可算）
请求吞吐、输出token吞吐、SLO达标率/goodput（如可算）
实际batch/排队/KV/抢占/通信资料是否存在
```

### 吞吐和 goodput

```text
成功请求吞吐 = 完成成功请求数 / 明确测量时长
成功输出吞吐 = 对应成功请求输出token总数 / 同一时长
request goodput = 满足所有指定SLO的成功请求数 / 同一时长
```

记录失败和无法判断 SLO 的请求，不能从分母中无说明删去；不同工具对测量边界取消请求的处理可能不同，应独立列数。

不要用 `1 / 平均 TPOT` 当系统输出吞吐；也不要把各请求生成速率相加冒充实测吞吐。

机器归一化吞吐可按实际机器数另报；NPU归一化吞吐需要实际NPU数。机器成本不同还需真实成本，不把双机 TPOT 除以 2。

### 判断运行区间

- 吞吐随 C 增长且时延稳定：可能未充分利用，需进一步看真实 batch/资源。
- 吞吐趋平且 TTFT/排队上升：可能接近容量边界，不能仅凭一条均值断言。
- 长输出下出现时延/失败/抢占跳变：优先检查容量状态，不强行用平滑模型覆盖。
- 客户端 CPU/连接池饱和而 NPU空闲：先排查发生器，不调算子。

仅 5 档 C 不能精确识别全局最优并发。最优点应定义为“已测候选中的最优可行点”，必要时在转折区补测。

### 门禁

产物：operating_map.csv、regime_notes.md、图表数据。

无 SLO 时 goodput 留空；无时长时吞吐留空；不反推伪造。

## 步骤 5：建立可辨识性清单，再拟合

### 现有数据可以和不可以识别什么

| 想回答的问题 | 仅现有80条件能否回答 | 最小额外信息 |
|---|---|---|
| 已测 C/L 下哪种部署延迟更低 | 同口径且质量合格时可以 | 真实重复用于不确定性 |
| TPOT 差距是否缩小 | 可以做描述/区间分析 | 独立重复、真实长度 |
| 是否有 1/N 摊薄形态 | 可以检验候选形态 | 同负载语义与状态审计 |
| prefill 计算随输入长度怎样增长 | 不可：输入只有512 | 多档输入及服务端prefill观测 |
| NPU峰值带宽/算力、真实roofline位置 | 不可 | A2微基准、算子shape/bytes/FLOPs |
| 设定C对应的真实decode batch规律 | 不可仅凭C | 服务端batch时间序列 |
| GPU模拟器可直接预测A2 | 不可 | A2性能表、backend/通信校准 |
| KV容量/MLA内存占用 | 不可仅凭TPOT | 模型结构、runtime缓存布局、每rank实际占用 |
| 生产混合流量的最佳配置 | 不可：固定输入合成网格 | 真实分布/到达/相关性与留出重放 |
| PD差异是否纯由架构造成 | 不可：资源绑定不同 | 可比decode资源与受控实验 |

### 阶段工作量与容量账本

固定输入512时，输入/输出token比例约512/L，只表示token组成，不等于prefill/decode算力或耗时比例。长输出的单次P→D初始KV通常没有同比放大，但D侧保存和访问的上下文在增长。

在负载稳定、窗口可比且已独立测得各阶段容量时，可用保守约束：

```text
请求完成能力 <= min(P阶段请求能力, D阶段请求能力, 初始KV链路请求能力)
链路请求能力 ≈ 独立有效传输带宽 / 每请求实际交接字节
```

有启动延迟、竞争和重叠时需进一步校准，不能简单视为等式。D容量依赖本实验长度/context/batch，不能从一个短输出tok/s除以任意L外推。

若固定只有一台P、一台D，机器级1P1D配比没有任意搜索自由度；改变角色内卡数/并行或增加机器需明确资源约束与授权。

### 必须写 identifiability.md

每个待估参数列：数据支持、混杂、是否可估、额外采集、允许措辞。不能用回归软件给出一个数字就认为参数被识别。

## 步骤 6：拟合三个竞争解释，而不是只拟合想证明的模型

### 6.1 为什么 TPOT 可能先降后升

对首 token 后的 N=L-1 个生成间隔，若平均单步耗时随上下文近似线性：

```text
d(s,C) ≈ a(C) + b(C) × s
平均上下文 ≈ S + L/2
TPOT(L,C) ≈ a(C) + b(C) × (S + L/2) + A(C)/(L-1)
```

S使用核实后的固定实际输入；确认为512时S=512，若模板后固定为另一长度则保留原计划并按实际S分组。这个平均上下文公式仅对应固定长度、完整请求、理想逐步增长，不包含调度变化。b是经验相关项，不自动等于attention带宽代价。

因此：有限项可能随 1/N 降低，同时上下文项增加。不能把“长输出必然下降/必然收敛”作为模型前提。

### 6.2 固定每个 C，分别拟合两部署及差值

候选模型：

```text
K0：y = a
K1：y = a + A/N
K2：y = a + b × (S+L/2)/1000
K3：y = a + A/N + b × (S+L/2)/1000
```

对差值 y=TPOT_mixed-TPOT_disagg，也使用同样候选。只有 K1 且残余项小并稳定，才可讨论简单摊薄模型；K3 更好时要承认上下文相关差异。

不要把 K1 截距外推成已证明的无限长度极限；K3 本身可能无有限极限。

### 6.3 数据准入

- 主结构拟合只接受实际输入和输出已确认固定的完整请求估计。
- 变长输出、失败/抢占状态、配置切换应另分组；原有描述结果仍保留。
- 对纳入模型但包含失败的运行，显式说明其 TPOT 是条件于成功的；不能用模型选择掩盖幸存者偏差。
- 8 个长度点只适合少参数模型。不要给每格单独自由参数后宣称预测成功。

### 6.4 验证规则

1. 同一长度的所有重复必须留在同一折，不能请求随机拆分或将同一长度重复泄漏到训练/验证两侧。
2. 留一长度验证：训练其他长度、预测被留出的长度，记录 MAE/RMSE/相对误差。
3. 长输出压力验证：预先留出最大两档长度，用其余长度训练，再预测这两档。
4. 检查残差是否随长度系统弯曲、是否存在长输出状态变化。
5. 做去最短、去最长点敏感性；参数符号/量级不稳定时不解释物理意义。
6. 对重复运行用真实独立 run/时间块重采样；没有独立重复时不造置信区间。
7. 模型选择看留出误差、简单性和残差，不只看训练R²。多模型探索后的结论标记探索性。
8. 若误差超过预定容差，承认模型未验证；转分段状态解释或补测，不事后放宽容差。

### 6.5 长输出新增区间的耗时代理

固定实际输出时可算：

```text
D(L) = (L-1) × 平均TPOT(L)
tail_proxy(L1,L2) = [D(L2)-D(L1)] / (L2-L1)
```

用途：观察跨case新增长度的耗时代理，辅助区分平均摊薄与后段增长。

限制：这是两次不同负载实验的差分，不是同一个请求的真实后段ITL。只有批大小、到达和其他条件近似可比时才有较强解释。保留负值并排查，不截断为0。

## 步骤 7：把推论写成可以失败的假设卡

每张卡必须有：假设、前提、主对照、观察指标、预期反例、判定标准、当前证据、下一次最小实验。

### H1：有限扰动摊薄

支持：差值随长度减小；K1/K3中逆长度项有稳定贡献；有限额外量与实际事件累计相容。

反证/竞争解释：长输出改变补请求频率、初始填充/尾部batch效应、分离baseline随context增长、prefix命中不一致。

额外验证：同一稳定decode流中注入次数和规模受控的prefill，检查额外累计延迟是否随注入次数变化。需授权，不自动执行。

### H2：长上下文产生持续代价

支持：K2/K3对留出长度预测更好；同batch/相近状态下后段ITL升高；相关attention/KV事件增加。

反证：实际batch、路由、抢占或缓存布局变化解释全部趋势。仅b>0不证明HBM瓶颈。

### H3：并发存在吞吐与SLO的折中点

支持：实测吞吐与尾时延形成可行边界；在转折附近新增并发点复测。

反证：发生器/连接池限流，或运行未达稳态。不能把观测最大吞吐点当全局最优。

### H4：长输出触发KV/调度容量转折

支持：时延跳变与实际KV占用、分配失败、抢占/重计算事件共现，并有受控改变容量后的转折移动。

反证：仅内存使用率高，没有容量事件；或时间段背景负载改变。

### H5：PD在指定SLO/成本下更优

支持：明确资源边界，比较同负载SLO达标率、goodput及每机器/每NPU效率。

反证：分离TPOT更低但TTFT/失败/成本更差；或者一机vs双机差异不能归为架构优势。

## 步骤 8：按症状选择少量采集，不先 profile 全部80格

### 初始哨兵

先考虑每部署三个条件：C1/L512、C8/L8192、C32/L65536；再选一个数据驱动的异常格。总计最多8个条件作为初轮候选，不代表全部必须跑。

每个采集条件先跑无profiler基线。长请求只采经过版本验证的有限窗口，避免全程65536 token的海量trace；若工具不支持所需窗口，不编造延迟启动/attach能力。

### 证据表

| 症状 | 优先核查 | 不能直接下的结论 |
|---|---|---|
| TTFT高、TPOT尚稳 | 客户端派发、队列、prefill、PD交接关键路径 | TTFT就是prefill计算 |
| TPOT高、实际batch低 | 调度供给、kernel launch、权重读取、通信占比 | 一定HBM带宽不足 |
| 长输出后段变慢 | 真实context/batch、attention/KV、抢占 | 一定固定扰动摊薄失效 |
| 高C吞吐趋平 | 资源饱和、队列、发生器限制 | C=32一定硬件满载 |
| PD分离额外开销 | KV交接、路由、通信与decode是否重叠 | 阶段时长简单相加就是E2E |
| MoE多rank差异大 | 专家负载、AllToAll、最慢rank关键路径 | 平均rank利用率足以说明效率 |

### PD交接的两个特殊检查

1. 常规一次交接通常传输入prompt对应的初始KV，本实验主要由输入512及实现决定；不能把最终65536输出当成一次65536-token的P→D传输量。重计算、迁移、分层异步或特殊connector另行建模。
2. 首token若由P直接返回，handoff可能主要落在首、次输出之间并进入TPOT，而不全在TTFT。先沿实际请求关联事件判断，不能预设所有交接都属于TTFT。

### 结构模型需要的真实采集

- 算子：shape、dtype、实际batch/context、耗时，避免把并行stream时长求和当关键路径。
- 计算：有效FLOPs定义；A2对应dtype的可达性能，非GPU峰值。
- 内存：实际读写/缓存布局、每rank KV容量与碎片，区分GB与GiB。
- 通信：TP/EP/PD分别分类、数据量、拓扑、等待和可重叠部分。
- 调度：prefill/decode起止、实际batch、排队、抢占与重计算。

只在shape/操作/单位匹配时用下界：

```text
t_step >= max(FLOPs / 有效算力, 访存字节 / 有效带宽, 必要通信下界)
```

这不是等式；不同阶段的串并行、重叠与固定开销要由trace校准。不能从TPOT反算带宽后再用同一带宽证明模型正确。

### 模型结构分支

Dense/GQA 可先做粗略逻辑KV估计：

```text
KV_bytes ≈ 层数 × 活跃序列context总和 × 2 × KV头数 × head_dim × dtype_bytes
```

MLA、稀疏/压缩attention、混合cache、跨rank复制需按真实实现重写；不能给所有DeepSeek模型套Dense公式，也不能一律除以TP。MoE需区分驻留权重内存与每token激活专家计算。

### 门禁

产物：profile_plan.md、trace_manifest.csv、bottleneck_evidence.md、calibration_table.csv。

采集命令必须来自本机stack/版本和已验证官方路径。无服务端权限则停在M0/M1，不编造M2。

## 步骤 9：从证据生成优化候选

每项写 optimization_card.md：

```text
问题/证据/竞争解释
支持的stack与版本/已验证参数来源
单个改动/其余保持不变/回滚命令
主收益指标/护栏指标/预计影响范围
可能回归/正确性风险/复测case
通过标准/失败标准/是否获执行授权
```

### 候选映射

| 证据 | 优先考虑 | 必须防的回归 |
|---|---|---|
| prefill与decode窗口竞争 | 版本支持的chunk/budget/调度策略 | TTFT、公平性和吞吐下降 |
| 实际batch不足且资源有余量 | 调度供给、合批、连接/派发瓶颈 | 隐藏排队、尾时延 |
| KV容量事件明确 | cache预算/布局/碎片、可支持的KV dtype | OOM、精度、额外重计算 |
| context相关attention占主导 | 已支持的融合kernel/缓存路径 | 不可用截断/sliding-window偷改语义 |
| TP/EP通信主导 | 可比资源下的并行/放置配置 | 权重容量、路由不均、跨节点瓶颈 |
| PD交接主导 | 实际KV布局、传输/调度重叠、P/D资源配比 | TTFT和P端饥饿 |
| 客户端限流 | 连接池/CPU/解析与发送实现 | 请求率口径改变、客户端耗尽 |
| 量化收益假设 | 独立精度与kernel支持验证 | 不能只用长输出速度替代正确性 |
| prefix cache命中不公平 | 先统一实验条件并单独报告命中 | 不能把缓存复用当架构本身优势 |

不提供跨backend万能参数。参数名称、取值上限和依赖必须从当前安装版 --help、配置schema或源码确认。

若某可优化关键路径分量占比为p，理想完全消除该分量的加速上界约为 1/(1-p)；有重叠/排队时需另算，不能将算子占时简单等同端到端可优化比例。

### 排序

优先级依据：证据强度、SLO/goodput预期收益、实现成本、正确性风险、回滚难度。没有实测p时不填虚构收益百分比。

## 步骤 10：优化验证和回归

1. 冻结候选之前的baseline和原始配置，保存版本/hash。
2. 从一项低风险、证据最强的改动开始；不要同时改调度、并行和dtype。
3. 在相同输入、输出、发压方式、种子与可比时间块下做A/B或随机顺序重复。
4. 优化参数若改变允许并发或请求率，明确区分“同负载性能提升”和“重新选择运行点”；不能混写。
5. 先验证目标格，再回归短/长、低/高C、异常格；最终预算允许时回归全部80条件。
6. 比较成功率、正确性、TTFT/TPOT/E2E、尾分位、goodput、吞吐和资源，不只看平均TPOT。
7. 以独立run/时间块计算区间；同一run的请求不冒充独立实验。
8. 包含冷启动/预热边界、profiler开销对照。不可将profiled baseline与unprofiled candidate混比。
9. 若有SLO，区间与风险合格才接受；若无SLO，报告Pareto变化和代价，不宣称生产最优。
10. 任何正确性退化、失败率明显变差或非目标格严重回归，都进入拒绝/回滚流程。

产物：ab_plan.md、ab_results.csv、regression_matrix.csv、decision.md。

## 步骤 11：最终交付

必须包含：

1. 一页决策摘要：哪些结论已支持、反对、证据不足。
2. 每个C的独立结论；缺失和反例不可省略。
3. 真实负载/资源/计时口径、成功率与实际长度。
4. M0结果、M1模型与留出误差、M2是否具备真实校准。
5. 已排除/尚未排除的竞争解释。
6. 优化候选排序、执行权限、已执行和未执行的区别。
7. A/B和回归结果；没有执行就写“建议”，不能写“已提升”。
8. 适用域：S=512、已测C/L、当前模型/精度/stack/拓扑；超域预测单独标记。
9. SOURCES.md、来源版本、复现命令、输入/脚本hash、产物清单。

### 最终禁止用语

- “已证明所有长输出都会收敛到PD分离。”
- “拟合R²很高，因此找到了硬件瓶颈。”
- “NPU利用率高，所以一定是算力瓶颈。”
- “只测输入512，已经建立任意输入长度的prefill模型。”
- “GPU模拟器结果就是A2结果。”
- “单次运行有32个请求，所以有32次独立重复。”
- “只调整输出截断/模型语义即可算性能优化。”

# PD分离与 PD混部：性能实测、底层剖析与选型指南（单卡吞吐与SLA维度版）

> 2026-11-22｜`1K = 1024 tokens`｜基准：8卡 PD 混部 vs 16卡 PD 分离

在大语言模型（LLM）推理服务部署中，Prefill（首 Token 生成）与 Decode（增量 Token 生成）阶段在计算密集度、访存特征与 KV Cache 占用上存在本质差异：Prefill 属于计算受限型（Compute-Bound），Decode 属于访存受限型（Memory-Bound）。

此前由于缺少 PD 分离与 PD 混部在不同业务场景下的系统性能对照，团队容易陷入“直接比拼系统总吞吐”的误区——忽略了 PD 分离往往占用更多卡数，导致把“加卡带来的规模红利”误判为“架构天生的高效率”。

本文基于 Ascend 910B3（A2）实测数据与性能建模，**统一以单卡吞吐（tok/s/NPU）为核心算力效率度量指标**，深入对比 8 卡 PD 混部与 16 卡 PD 分离在不同上下文长度、输出长度及并发下的表现，剖析时延与吞吐瓶颈的底层成因，并提供可推广至其他 NPU 平台的部署建模与配卡方法。

---

## 1. 选型速览与指标口径

### 1.1 部署架构定义
* **PD 混部（Hybrid）**：在同一推理实例内交替或并行完成 Prefill 与 Decode，两阶段共享 GPU/NPU 算力与 HBM 显存资源。
* **PD 分离（Disaggregated）**：将 Prefill 和 Decode 拆分至独立的物理实例池，分别进行并行度配置与显存优化；请求完成 Prefill 后，通过网络交接 KV Cache 至 Decode 池。

### 1.2 评估指标口径

| 指标 | 测量标准与计算口径 | 架构评估定位 |
|---|---|---|
| **TTFT** | 首 Token 时延。从客户端发起请求至收到首个 SSE `data` 行。评估主要看平均值，最短值（min）用于硬件纯计算极限对照。 | 主要由 Prefill 阶段计算耗时、Prefill 队列排队及网络传输决定。 |
| **TPOT** | 首 Token 后的平均 Token 生成间隔。单请求计算式：$$\text{TPOT} = \frac{\text{E2E} - \text{TTFT}}{N_{\text{out}} - 1} \quad (N_{\text{out}} > 1)$$ 本文采用批次内所有请求的平均值进行对比。 | 主要由 Decode 阶段访存带宽、Batch Size 及 Prefill 抢占干扰程度决定。 |
| **单卡吞吐（核心）** | $\text{整套输出吞吐} \div \text{整套 NPU 总数}$，单位：`tok/s/NPU`。PD 分离的卡数包含 P 池与 D 池卡数之和。 | **评估算力利用效率与成本效益的硬指标**。选型与建模均以此为准。 |
| **成功 QPS** | 持续回放下，统计窗口内成功完成的请求数 $\div$ 统计窗口时长（请求/秒）。 | 业务容量规划指标。 |
| **cc** | 压测客户端设定的并发数（Concurrency Count）。 | 负载压力测试变量。 |

*注：在架构横向对比中，单纯对比“批次总吞吐”是没有意义的，因为测试基准中 PD 分离使用 16 卡，PD 混部使用 8 卡。只有当 PD 分离的单卡吞吐（tok/s/NPU）超越 PD 混部时，分离架构才具备算力效率上的优势。*

### 1.3 测试基准环境
端到端对照实验统一采用 `Block128` 规格，模型为 **DeepSeek-V4-Flash-0731 w8a8**，推理引擎为 `vllm-ascend v0.30.0rc2`。
* **8 卡 PD 混部**：1 组 8 × Ascend 910B3（64 GB HBM/NPU），TP8 + EP 架构。
* **16 卡 PD 分离**：池化部署，P 池与 D 池合计 16 卡（硬件规模为混部的 2 倍）。
* **测试用例划分**：
  1. `in512` 短输入：固定 cc，扫描输出长度（512 ~ 64K）。
  2. `in4K / out2K` 中等长文本：固定输入输出，扫描并发（cc4 ~ cc128）。
  3. `in64K / out8K` 超长上下文：固定输入输出，扫描并发（cc4 ~ cc128）。

详见 [附录 A](#appendix-a)、[附录 C](#appendix-c)、[附录 G](#appendix-g)、[附录 H](#appendix-h)。当同一条件有多条记录时，正文统一取记录号最小的一条。

## 2. 实测对照与底层性能剖析

### 2.1 TTFT 分析：Prefill 瓶颈与并发爆仓现象

#### 场景 1：in512 短输入，看输出长度影响
在 `in512, cc8` 条件下，PD 混部的平均 TTFT 在各个输出长度下均优于 PD 分离（混部 1.06～1.12 秒，分离 1.45～1.65 秒）。PD 分离由于引入了 RPC 路由调度与跨节点 KV Cache 传输开销，在低并发、短输入的轻载场景下存在固定时延劣势。

![图 1：in512、cc8 下PD混部与PD分离的平均 TTFT 随输出长度变化](./pd_figures_terms/01_ttft_length.png)

| 输出长度 | PD混部平均 TTFT（秒） | PD分离平均 TTFT（秒） | 性能特征说明 |
|---|---|---|---|
| 512 | 1.12 | 1.60 | 混部低时延优势明显 |
| 2K | 1.10 | 1.55 | - |
| 8K | 1.06 | 1.45 | - |
| 16K | 1.07 | 1.52 | - |
| 32K | 1.08 | 1.65 | - |

当并发提升至 **cc64** 时发生拐点：
* `out16K`：PD 混部平均 TTFT 依然较低（混部 2.16 秒 vs 分离 2.49 秒）。
* `out32K`：PD 混部 TTFT 发生剧烈排队暴涨升至 **55.14 秒**，而 PD 分离仅为 **14.23 秒**。若进一步升至 `out64K`，PD 混部的平均 TTFT 进一步恶化至 **572.16 秒**。
* **原因剖析**：PD 混部实例在长文本+高并发下，显存大量被增量 KV Cache 占用，导致 Prefill 阶段可用的 Continuous KV Block 不足，新请求被迫在 Engine Queue 中长时间等待；而 PD 分离的 P 池显存专用于 Prefill，不随 Decode 长度膨胀而耗尽。

#### 场景 2：in4K / out2K 中长文本，看并发梯次
在所有已测并发档（cc4 ~ cc128）中，PD 混部的平均 TTFT 均低于 PD 分离。

![图 2：in4K/out2K 下两种部署的平均与最短 TTFT 随并发变化（Block128）](./pd_figures_terms/01_ttft_4k2k_block128.png)

| cc | PD混部平均 TTFT（秒） | PD分离平均 TTFT（秒） | PD混部最短 TTFT（秒） | PD分离最短 TTFT（秒） |
|---|---|---|---|---|
| 4 | 1.455 | 1.853 | 0.927 | 1.060 |
| 8 | 1.980 | 2.323 | 0.907 | 1.050 |
| 16 | 2.948 | 3.356 | 0.912 | 1.054 |
| 32 | 3.450 | 5.471 | 0.882 | 1.062 |
| 64 | 8.276 | 15.738 | 0.920 | 1.057 |
| 128 | 20.881 | 40.442 | 0.938 | 1.060 |

两套部署的最短 TTFT（min）在各并发档下几乎保持恒定（混部约 0.91s，分离约 1.06s），这代表了没有任何排队时的硬件纯计算耗时。平均 TTFT 的上升完全是由并发排队导致的。在 `in4K/out2K` 负载下，16 卡 PD 分离的平均 TTFT 劣于 8 卡混部，主要是因为分离架构下该负载尚未压爆混部的 Prefill 资源，而分离架构的网络传输与池化调度带来了额外的延迟固定开销。

#### 场景 3：in64K / out8K 超长上下文
在超长上下文场景下，Prefill 的计算开销极其巨大。

| cc | PD混部 TTFT：平均值 / 最短值（秒） | PD分离 TTFT：平均值 / 最短值（秒） | 性能拐点判定 |
|---:|---:|---:|---|
| 4 | 19.78 / 13.01 | 20.66 / 13.74 | 低并发下混部微弱领先 |
| 8 | 25.49 / 13.03 | 27.89 / 13.64 | 混部微弱领先 |
| **16** | **237.49** / 13.07 | **96.83** / 13.59 | **拐点到来：混部出现严重的 Prefill 阻塞** |
| 32 | 674.90 / 13.03 | 276.55 / 13.66 | 分离优势进一步扩大 |
| 64 | 1535.78 / 13.09 | 637.47 / 13.68 | 混部严重爆仓 |
| 128 | 3282.12 / 13.09 | 1346.02 / 13.60 | 混部不可用 |

从 **cc16** 开始，PD 混部的 Prefill 阶段彻底陷入资源饥饿，平均 TTFT 骤增至 237 秒；而 PD 分离由于拥有独立的 P 池资源隔离，平均 TTFT 仅为 96.8 秒（降幅达 59.2%）。

### 2.2 TPOT 分析：Decode 算力与显存带宽隔离优势

与 TTFT 的动态博弈不同，**在所有测试场景及并发梯次中，PD 分离的平均 TPOT 均显著低于 PD 混部**。

#### 场景 1：in512 下输出长度对 TPOT 的影响

![图 3：in512 下PD混部与PD分离的平均 TPOT 随输出长度变化，分别比较 cc8 和 cc64](./pd_figures_terms/02_tpot_length.png)

| 输出长度 | PD混部 cc8 平均 TPOT（ms） | PD分离 cc8 平均 TPOT（ms） | PD混部 cc64 平均 TPOT（ms） | PD分离 cc64 平均 TPOT（ms） | cc64 档 PD分离优势 |
|---|---|---|---|---|---|
| 512 | 31.6 | 23.4 | 87.2 | 27.5 | **降低 68.5%** |
| 2K | 20.5 | 17.2 | 50.8 | 21.8 | **降低 57.1%** |
| 8K | 17.0 | 14.8 | 36.5 | 17.3 | **降低 52.6%** |
| 16K | 15.9 | 13.0 | 33.4 | 16.6 | **降低 50.3%** |
| 32K | 15.6 | 12.8 | 32.2 | 16.3 | **降低 49.4%** |

#### 场景 2：in4K / out2K 下并发对 TPOT 的影响

![图 5：in4K/out2K 下两种部署的平均 TPOT 随并发变化（Block128）](./pd_figures_terms/02_tpot_block128.png)

| cc | PD混部平均 TPOT（ms） | PD分离平均 TPOT（ms） | PD分离优势 |
|---|---|---|---|
| 4 | 19.4 | 15.9 | 18.0% |
| 8 | 22.2 | 16.5 | 25.7% |
| 16 | 29.1 | 17.0 | 41.6% |
| 32 | 25.9 | 17.5 | 32.4% |
| 64 | **61.6** | **19.3** | **降低 68.7%** |
| 128 | **148.5** | **18.3** | **降低 87.7%** |

#### 场景 3：in64K / out8K 下并发对 TPOT 的影响

| cc | PD混部平均 TPOT（ms） | PD分离平均 TPOT（ms） | 备注 |
|---:|---:|---:|---|
| 4 | 14.6 | 13.3 | 混部与分离均满足 <20ms 限制 |
| 8 | **27.5** | 13.8 | 混部超过 20ms |
| 16 | **27.6** | 14.7 | 混部超过 20ms |
| 32 | **28.0** | 11.5 | 混部超过 20ms |
| 64 | **28.2** | 14.2 | 混部超过 20ms |
| 128 | **28.6** | 14.1 | 混部超过 20ms |

Decode 阶段属于典型的访存受限型操作。在 PD 混部架构中，即使只来了少量 Prefill 请求（计算受限型），其大矩阵乘法也会瞬间抢占 NPU 的 Vector/Tensor 核心以及 HBM 总线带宽，导致正在进行的 Decode 步骤产生严重的 Bubble（空泡排队）。
而在 PD 分离架构中，D 池只处理 Decode 步骤，Batch 内所有请求的增量 Token 生成节奏极度稳定，因此其 TPOT 随并发增长波动极小（始终稳定在 11~19ms），体现了绝对的资源隔离优势。

### 2.3 吞吐对比：聚焦单卡效率（tok/s/NPU）

评估算力产出时，**单卡吞吐（tok/s/NPU）才是横向衡量架构效率与硬件投资回报率的唯一公平指标**。下文摒弃总吞吐对比，直接分析单卡吞吐在不同场景下的表现与反超拐点。

#### 场景 1：in512 下单卡吞吐随输出长度变化

![图 6：in512、cc64 下PD混部与PD分离的单卡输出吞吐随输出长度变化](./pd_figures_terms/03_throughput_length.png)

| 输出长度 | PD混部单卡吞吐（tok/s/NPU） | PD分离单卡吞吐（tok/s/NPU） | 单卡效率对比 |
|---|---|---|---|
| 512 | 82.39 | **104.71** | PD 分离领先 27.1% |
| 2K | 134.73 | **138.63** | PD 分离领先 2.9% |
| 8K | **202.18** | 198.33 | PD 混部领先 1.9% |
| 16K | **221.64** | 197.13 | PD 混部领先 12.4% |
| 32K | 187.79 | **195.66** | PD 分离领先 4.2% |

在 `in512, cc64` 条件下：
* 当输出为 8K、16K 时，PD 混部的单卡效率更高（在 out16K 达到峰值 **221.64 tok/s/NPU**）。这意味着如果拥有 16 张卡，部署 **2 组 8 卡 PD 混部** 的总产出（约 3546 tok/s）将显著高于 **1 组 16 卡 PD 分离**（3154 tok/s）。
* 当输出延长至 32K 时，PD 混部因显存挤压与长尾排队导致单卡吞吐回落至 187.79 tok/s/NPU，而 PD 分离在 D 池显存隔离保护下仍能维持 195.66 tok/s/NPU，单卡效率实现反超。

#### 场景 2：in4K / out2K 下单卡吞吐随并发变化

![图 7：in4K/out2K 下两种部署的单卡吞吐随并发变化（Block128）](./pd_figures_terms/03_throughput_per_npu_block128.png)

| cc | PD混部单卡吞吐（tok/s/NPU） | PD分离单卡吞吐（tok/s/NPU） | 单卡效率差异 |
|---|---|---|---|
| 4 | **22.41** | 13.32 | 混部高 40.6% |
| 8 | **39.96** | 24.26 | 混部高 39.3% |
| 16 | **53.70** | 40.53 | 混部高 24.5% |
| 32 | **128.09** | 81.68 | 混部高 36.2% |
| 64 | 111.17 | **115.56** | **分离微弱高 4.0%** |
| 128 | **93.10** | 70.59 | 混部高 24.2% |

在 `in4K/out2K` 场景下：
* 8 卡 PD 混部在 **cc32** 展现出极高的单卡产出效率（**128.09 tok/s/NPU**），显著优于同期 PD 分离的 81.68 tok/s/NPU。
* 只有当并发飙升至 cc64 时，PD 混部因内部资源争抢严重发生性能衰退（降至 111.17 tok/s/NPU），PD 分离才以 115.56 tok/s/NPU 出现微弱反超。
* 结果表明：在中等上下文场景下，如果仅以单卡吞吐最大化为目标，**PD 混部架构在大部分并发区间具备更高的算力性价比**。

#### 场景 3：in64K / out8K 下单卡吞吐的效率逆转

在超长上下文负载下，由于 Prefill 耗时极其巨大且严重干涉 Decode，PD 分离的单卡效率实现了彻底逆转。

| cc | PD混部单卡吞吐（tok/s/NPU） | PD分离单卡吞吐（tok/s/NPU） | 单卡效率对比与拐点判定 |
|---:|---:|---:|---|
| 4 | **19.11** | 14.81 | 混部领先 |
| 8 | **31.44** | 25.19 | 混部领先 |
| 16 | **31.27** | 31.11 | 基本持平 |
| **32** | 32.57 | **37.15** | **拐点到来：PD分离单卡效率反超 14.1%** |
| 64 | 33.12 | **38.31** | PD分离单卡效率领先 15.7% |
| 128 | 32.85 | **39.44** | PD分离单卡效率领先 20.1% |

在 `in64K/out8K` 场景下：
* 在 cc4~cc16 较低并发下，PD 混部单卡吞吐占优。
* 从 **cc32** 开始，PD 分离的单卡吞吐（37.15 tok/s/NPU）正式反超 PD 混部（32.57 tok/s/NPU）。这证明在超长上下文+高并发场景下，PD 分离不仅能解决排队问题，其硬件算力利用效率也超越了混部。

### 2.4 决策模型：基于 SLA 约束与单卡效率的双重选型路径

选型决策应当遵循**“先用 SLA（TTFT & TPOT）过滤无效档位，再按单卡吞吐最高原则选择架构与扩展方式”**的逻辑：

```
                    [输入业务 SLA 限制与目标 QPS]
                                 │
                                 v
          [剔除 TTFT 或 TPOT 超过 SLA 限制的并发档位]
                                 │
                                 v
          [比较各架构在达标档位下的 Max(单卡吞吐 tok/s/NPU)]
                                 │
         ┌───────────────────────┴───────────────────────┐
         │                                               │
 [混部单卡吞吐 > 分离单卡吞吐]                     [分离单卡吞吐 > 混部单卡吞吐]
         │                                               │
         v                                               v
 选用 8卡 PD混部 实例                     选用 PD分离 架构部署
 (若单实例总吞吐不足，                                (按 P:D 配比池化部署)
  优先采用 N 组混部水平扩容)
```

![图 1b：in512 PD混部，out16K 与 out32K 的平均 TTFT 和单卡吞吐随并发变化](./pd_figures_terms/05_output_length_throughput_ttft.png)

![图 8：in64K/out8K 下PD混部与PD分离的并发对照：上图为平均 TTFT，下图为单卡吞吐](./pd_figures_terms/05_ttft_capacity_64k8k.png)

#### 选型实战推演案例：

1. **案例 A：in512 / out16K（SLA 要求：TTFT ≤10s, TPOT ≤35ms，总吞吐目标 ≥2500 tok/s）**
   * **档位筛选**：PD 混部 cc64（TTFT 2.16s, TPOT 33.4ms）与 PD 分离 cc64（TTFT 2.49s, TPOT 16.6ms）均满足 SLA。
   * **效率比拼**：8 卡混部 cc64 的单卡吞吐为 **221.64 tok/s/NPU**；16 卡分离 cc64 的单卡吞吐为 **197.13 tok/s/NPU**。混部单卡效率高出 12.4%。
   * **决策**：虽然 8 卡混部单组总吞吐（1773 tok/s）未达到 2500 tok/s 目标，但由于其单卡效率更高，**最优方案是部署 2 组 8 卡 PD 混部（共16卡）**。其总产出可达 `221.64 × 16 ≈ 3546 tok/s`，相比部署 16 卡 PD 分离（产出 3154 tok/s）能多获得约 12.4% 的算力产出。

2. **案例 B：in4K / out2K（SLA 要求：TTFT ≤6s，总吞吐目标 ≥1000 tok/s）**
   * **场景 B1（TPOT 宽松上限 ≤30ms）**：
     * PD 混部在 cc32 达标（TTFT 3.45s, TPOT 25.9ms），单卡吞吐达 **128.09 tok/s/NPU**（单组总吞吐 1025 tok/s 直接达标）。
     * 决策：选用 **1 组 8 卡 PD 混部**。
   * **场景 B2（TPOT 严苛上限收紧至 ≤20ms）**：
     * PD 混部在 cc8~cc128 的 TPOT 均 >20ms 超标，仅 cc4 满足（TPOT 19.4ms），但 cc4 单卡吞吐仅 22.41 tok/s/NPU（8 卡总吞吐仅 179 tok/s），要达到 1000 tok/s 需要部署 6 组（48 卡），极大浪费算力。
     * PD 分离在 cc32 仍能稳定维持 TPOT 17.5ms（达标），单卡吞吐为 **81.68 tok/s/NPU**（16 卡总吞吐 1307 tok/s 达标）。
     * 决策：由于混部在硬性 TPOT 限制下发生了严重的吞吐退化，**改选 16 卡 PD 分离**。

3. **案例 C：in64K / out8K（SLA 要求：TTFT ≤100s, TPOT ≤30ms）**
   * **档位筛选**：PD 混部最高只能达到 cc8（TTFT 25.49s, TPOT 27.5ms，cc16 时 TTFT 暴涨至 237s 超标被排除）；PD 分离最高可达到 cc16（TTFT 96.83s, TPOT 14.7ms）。
   * **效率比拼**：混部 cc8 档单卡吞吐为 31.44 tok/s/NPU；分离 cc16 档单卡吞吐为 **31.11 tok/s/NPU**。两者单卡效率相当。
   * **决策**：若业务目标吞吐 ≤250 tok/s，选用 **8 卡 PD 混部**；若业务目标 >250 tok/s（如要求 500 tok/s），由于混部扩并发会遭遇 TTFT 爆仓，必须选用 **16 卡 PD 分离**。

### 3.2 跨 NPU 平台通用性能建模与 P:D 配比推导

当迁移至其他 NPU 硬件平台时，无需重新测试所有组合。架构选型与容量配比应当**直接从 Prefill 侧与 Decode 侧的 QPS 算力瓶颈出发**，按以下四步法进行建模与验证：

```
[1. 业务负载与 SLA 锚定] ──> 确定 Prompt/Completion 长度分布及 TTFT, TPOT SLA
                                  │
                                  v
[2. 纯 P / 纯 D 阶段 QPS 测定] ──> 在 SLA 约束下分别测出 1个P单元 QPS_P 与 1个D单元 QPS_D
                                  │
                                  v
[3. 推导 P:D 单元初始配比] ──> 按流量守恒计算 N_P : N_D = QPS_D : QPS_P
                                  │
                                  v
[4. 全链路端到端压测定型] ──> 比较 PD分离(配比组合) 与 PD混部(多实例) 的单卡效率
```

#### P:D 单元配比数学推导（基于 QPS）
在 PD 分离架构中，任何一个完成的端到端请求都必须依次在 Prefill 侧和 Decode 侧各被处理一次。设：
* $QPS_P$：在满足平均 TTFT SLA 上限前提下，**1 个纯 Prefill 测试单元**（如 8 卡）能稳定承受的最大请求速率（`req/s`）。
* $QPS_D$：在满足平均 TPOT SLA 上限前提下，**1 个纯 Decode 测试单元**（如 8 卡）能稳定承受的最大请求速率（`req/s`）。

为使全系统在稳态运行时 Prefill 池与 Decode 池的吞吐完全匹配、无单侧积压阻塞，必须满足：
$$\text{P 池总请求处理能力} = \text{D 池总请求处理能力}$$
$$N_P \times QPS_P = N_D \times QPS_D$$

由此推导出 **P:D 初始单元数配比公式**：
$$\frac{N_P}{N_D} = \frac{QPS_D}{QPS_P} \implies P : D = QPS_D : QPS_P$$

即：**1 个 Decode 单元每秒能处理 $M$ 个请求，1 个 Prefill 单元每秒能处理 $N$ 个请求，则 P:D 单元数配比初始设为 $M : N$**。

*(实测验证：参考 [附录 D](#appendix-d)，在 `in4K/out2K` 负载下，1 个 8 卡纯 P 单元在时延限制内可承载 $QPS_P = 1.2539 \text{ req/s}$；1 个 8 卡纯 D 单元在 TPOT ≤20ms 内可承载 $QPS_D = 1.2426 \text{ req/s}$。因此 $P:D \approx 1.2426 : 1.2539 \approx 1 : 1$。按此配比测试，即为 **1 个 P 单元（8卡）配 1 个 D 单元（8卡）**，合计 16 卡。)*

#### 业务容量与所需单元数核算
设业务峰值流量需求为 $QPS_{\text{target}}$：
* 所需 Prefill 单元数：$N_P = \lceil QPS_{\text{target}} / QPS_P \rceil$
* 所需 Decode 单元数：$N_D = \lceil QPS_{\text{target}} / QPS_D \rceil$
* PD 分离总卡数：$\text{NPU}_{\text{Disag}} = (N_P \times NPU_P) + (N_D \times NPU_D)$

最终在全链路端到端压测中，计算**分离架构实际单卡吞吐**：
$$\text{Capacity}_{\text{Disag}} = \frac{QPS_{\text{actual}} \times N_{\text{out}}}{\text{NPU}_{\text{Disag}}} \quad (\text{tok/s/NPU})$$

将其与相同卡数预算下的**多组 PD 混部单卡吞吐**对比。若 $\text{Capacity}_{\text{Disag}} > \text{Capacity}_{\text{Hybrid}}$，或者混部由于资源争抢打爆了 SLA，则定型选择 PD 分离。

### 3.3 建模实战案例：24 卡预算下的硬件选型推演

#### 场景假设
* **硬件预算**：某新型 NPU 平台，卡数总预算为 **24 卡**（每 8 卡为 1 个物理单元）。
* **业务负载与 SLA**：`in4K / 实际 out2K`，峰值到达 QPS = **0.60 req/s**（即总体产出需求 1200 tok/s）。SLA 要求：平均 TTFT ≤6 秒，**平均 TPOT ≤30 ms**。

#### 选型推演过程

```text
[第一阶段：纯 P / 纯 D 阶段 QPS 测定与配比推导]
  1. 测得 1个 8卡纯 P单元在 TTFT ≤6s 时，最大 QPS_P = 0.80 req/s
  2. 测得 1个 8卡纯 D单元在 TPOT ≤30ms 时，最大 QPS_D = 0.40 req/s
  3. 计算 P:D 初始单元数比例：
     P:D = QPS_D : QPS_P = 0.40 : 0.80 = 1 : 2
  4. 按 24卡预算计算所需单元数：
     - N_P = ceil(0.60 / 0.80) = 1 个 P单元 (8卡)
     - N_D = ceil(0.60 / 0.40) = 2 个 D单元 (16卡)
     - 合计 24卡，完美匹配 1P + 2D 组合。

[第二阶段：方案横向对比]
  - 方案甲：24卡 PD分离 (1P + 2D)
    * 在 0.60 req/s 回放下实测：TTFT = 4.8s, TPOT = 18ms (均达标)
    * 整体单卡吞吐 = 1200 tok/s ÷ 24卡 = 50.0 tok/s/NPU

  - 方案乙：24卡 PD混部 (部署 3组 8卡混部实例，流量均分)
    * 每组混部实例承载 0.20 req/s (折合并发约 cc12)
    * 单组实测：在 cc12 下，TTFT = 2.4s, TPOT = 23ms (均达标)
    * 整体单卡吞吐 = 51.2 tok/s/NPU (总产出 1228.8 tok/s)

[第三阶段：选型决选]
  - 在满足 SLA 前提下，方案乙（3组 8卡混部）的单卡吞吐 (51.2 tok/s/NPU) 略优于方案甲 (50.0 tok/s/NPU)。
  - 结论：选用 3 组 8卡 PD混部，架构更为简单且无需搭建跨节点 KV 传输网络。
  - 变数补充：若业务将 TPOT SLA 进一步收紧至 ≤20ms，混部在 cc12 下 TPOT(23ms) 超标衰退，此时则必须改选 24卡 PD分离 (1P+2D) 方案。
```
